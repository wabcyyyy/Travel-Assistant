# Travel-Assistant 代码审计报告

> 审计日期：2026-09-09
> 审计范围：travel-agent-python（Agent/RAG/数据管线）、travel-backend-java（编排/安全）、travel-frontend-vue（交互/契约）
> 审计方式：三层分区逐文件精读 + 关键发现交叉验证（只读，未改动代码）

## 总体评价

架构口径清晰（LLM-only 开放模式、如实降级、引用落地），注释自觉；SQL 注入、XSS、水平越权等常见安全面基本干净。
主要风险集中在三块：

1. **降级路径的"最后一公里"不可达**（与定稿口径直接冲突）；
2. **信任边界模糊**（LLM 输出、客户端传入 context/plans/feedback 缺 schema 级校验；服务间鉴权默认静默关闭）；
3. **全栈契约丢失**（Python 的 degraded/status_reason 到 Java DTO 被抹平）。

---

## 一、Critical

### C1. 多日 LLM 失败：既不重试，"待研究草案"也是死代码
- 位置：`travel-agent-python/app/agent/workflow.py` L240-261、L288-299
- 多日 `attempt_limit=1`，开放模式整体失败返回 `{"error":..., "attempts":1}` 后，`needs_fix` 判 `1 < 1` False 直接 pass，`daily_plans` 仍为 `[]` → 最终 BLOCKED/failed。
- L251 的"待研究草案"分支只在 `attempts >= limit` 时进入，而错误分支后必然路由 pass——配置了 LLM key 时该分支永远不可达。
- 定稿口径"LLM 失败→重试一次→待研究草案（如实标注）"两个环节都落空。
- **修复**：错误分支同时返回带"待研究"note 的草案 plans；统一多日/单日重试语义（多日失败也允许一次重试）。

## 二、High

### H2. `format_output` 每次请求泄漏一个线程
- 位置：`workflow.py` L484-491
- 每请求 `new ThreadPoolExecutor` 且从不 `shutdown()`；`critique_plans` 是纯 CPU 函数，异步化无必要。
- **修复**：改为直接同步调用（保留 0.5s 语义无意义，删掉 executor）。

### H3. 路线服务开启后 ≥4 天行程必超工具预算
- 位置：`workflow.py` L61-72、L272-276、L474-482；`tool_registry.py` L237（`max_calls=8`）
- `_route_matrix_for_plans` 逐日 invoke，预算按整个 run 累计：reflect N 天 + format N 天 = 2N 次 → `ToolInvocationError` → 500。默认 `ROUTE_SERVICE_ENABLED=false` 掩盖。
- **修复**：一次 invoke 合并所有天 items（矩阵 key 为 (poi,poi)，跨天不冲突）。

### H4. 语义缓存"近似命中"在生产链路是死代码
- 位置：`app/rag/store.py` L292；`app/rag/cache.py` L105-119
- `cache.lookup` 从不传 `embedding_provider`，provider 为 None 时 cosine≥0.95 分支跳过；单测传了 provider 掩盖集成缺口。
- **修复**：store 传入 `self.embedding_provider`。

### H5. 服务间鉴权默认静默关闭（两端同病）
- 位置：`app/api/agent.py` L45-49、`app/common/config.py` L46；`AgentServiceImpl.java` L250-252
- `agent_internal_token` 为空即全放行；`/v1/generate` 烧真实 LLM token，`AGENT_HOST` 改 0.0.0.0 即匿名可用。
- **修复**：Python 启动时若绑定非回环地址且 token 为空 → fail-fast 拒绝启动。

### H6. Java `CallerRunsPolicy` 可自 DoS
- 位置：`config/AsyncConfig.java` L23；`ItineraryAsyncPlanner.java` L61；`RestTemplateConfig.java` L17（readTimeout 180s）
- 队列(50)打满后"异步生成"退化为在 Tomcat 请求线程内同步执行，可耗尽 HTTP 线程。
- **修复**：改 AbortPolicy + 拒绝转业务异常（建议项，本次未改，见遗留清单）。

### H7. 引用落地可被客户端 context 伪造 source
- 位置：`workflow.py` L376-393；`schemas/trip.py` L228；`generators.py` L286-302
- `/v1/generate-day` 的 `context` 是任意 dict，ReferencePool 直接信任其中 `source/open_time/ticket_price`；KB 行缺坐标时模型自填坐标仍被标 `partially_verified/observed`。
- **修复**：ReferencePool 构造时字段白名单清洗 + source 强制归一（非权威值域一律改写为 `client-context`）；坐标缺失不升级 observed。

### H8. LLM 输出未做结构校验即落地 + 客户端零重试
- 位置：`generators.py` L518（`_validate_plans` 定义但无调用点）；`workflow.py` L185-188、L422；`llm_client.py` L87-117
- 非 dict item → AttributeError → 500；`choices` 为空 → IndexError；429/5xx 无退避。
- **修复**：开放路径解析后统一过 `_validate_plans`；llm_client 对可重试错误加 1 次指数退避 + choices 判空。

## 四、整体设计问题

1. **三份相似编排并存**（workflow / day_stream / day_workflow）：needs_hotel 口径、fallback 真实性、ReferencePool 过滤三处行为不一致；建议收敛为单一生成内核 + 薄适配层。
2. **信任边界模糊**：外部输入（LLM 输出、客户端 context/plans/feedback）与服务端事实未分层校验。
3. **降级语义链路不完整**：Python→Java→前端的 status 枚举应共享定义并全链路透传。
4. **配置默认值偏演示友好**：token 空放行、DB root/空口令、route 服务默认关——生产应 fail-fast。
5. **测试结构失衡**：Python 单测绿但漏集成缺口（H4/H8/C1 均属"单测通过、生产死代码"）；Java 核心状态机零测试。

## 十三、管线重跑失败与二次修复（2026-09-10）

6 城管线采集全部成功（2051 条），但 `upsert_pois` 写库时崩溃：

1. `norm_name` 增加 `.casefold()`——Python 匹配粒度对齐（且略粗于）DB 唯一键，凡会撞键的必先归为同一行走 UPDATE。
2. `upsert_pois` INSERT 后把新行以 `cursor.lastrowid` 登记进 `existing`，批内后续同键记录走 UPDATE 合并。
