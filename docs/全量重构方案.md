### 0.4 五大核心原则（全方案不可破坏的底线）

本项目把「LLM 会编造」当第一性问题，可信是立身之本。以下五原则贯穿现有代码，**本方案第 2–7 章所有设计不得破坏**；每条架构决策（AD1–AD8）须逐条声明兼容性（收束于第 8 章）：

1. **LLM-only 内容来源**：行程内容 100% 由 LLM 生成；MySQL 权威 POI 库、Chroma RAG、web 检索只作证据输入，不直接拼装行程正文。
2. **引用式事实落地**：生成 Prompt 要求携带 `[R1..Rn]` 引用标记，落库时解析为 item 级 `source / verification_status / value_kind`，每个事实可回溯证据。
3. **开放模式诚实标注**：开放模式（web 检索）下地点保持 `unverified / before_departure` 标注，不因「写得好看」冒充已核实。
4. **降级如实呈现**：LLM 失败时返回待研究草案并如实告知，绝不拼装假行程、绝不静默填充内容。
5. **Prompt 定界符防注入**：用户输入进入 Prompt 一律定界符包裹 +「数据非指令」声明；重构后对新增 `intent` 字段同样适用（见 §1.1 V1/V5）。

### 1.1 产品价值断层：可信骨架强、意图感知弱（承档案 §1）

**同题对照事实**（京都 3 日 · 住柏悦 · 千恋万花圣地巡礼 · 预算约 5 万，详见档案 §1.1）：

| 维度 | 本项目输出（用户快照 · 行程 54） | 通用助手（豆包） |
|------|----------------------------------|------------------|
| 选点逻辑 | 伏见稻荷 → 金阁寺 → 西阵织，典型打卡 | 二年坂 / 花见小路 / 白川 / 旧武德殿 / 吉田山…主题点位 |
| 酒店理由 | 仅档次与价格 | 「酒店即在二年坂旁，步行 1–3 分钟进 CG 街区」 |
| 单点信息 | 来源标签 + 短描述（两行截断） | CG 对位、拍照机位、时段、礼仪 |
| 预算 | 分类汇总看板 | 分项拆表 + 为何这样花 + 降档方案 |
| 实用层 | 几乎无 | 预约、鞋、蚊虫、居民区礼仪、包车替代 |
| 方案分叉 | 无 | Day3 方案 A 神户 / 方案 B 留京都 |
| 主题贯通 | 全程无「千恋万花」字样 | 全程叙事主线 |

**根因不是模型「不会写」，是系统没要求它写**——七条断层全部可定位到代码：

| # | 断层 | 代码证据 | 直接后果 |
|---|------|----------|----------|
| V1 | 主题无一等输入通道 | `travel-frontend-vue/src/views/GenerateView.vue:202-209` 主表单仅 6 枚举标签 `PREFERENCE_TAGS`；自由意图只走可选 requirements 聊天拼接（`:220-222,395`） | 生成只能按泛标签选点 |
| V2 | 研究层不知主题 | `ResearchTask`（`travel-agent-python/app/agent/research/evidence.py:25`）仅 domain / city / preferences / budget / hotel_tier / limit，**无 theme / intent_keywords** | 检索与补查词围绕类目，不围绕作品 / 兴趣 / 事件 |
| V3 | 生成契约只要「规范景点列表」 | `_llm_open_day`（`travel-agent-python/app/agent/day_stream.py:88`）与 `_llm_open_trip`（`:183`）的 JSON 契约为 note + items + suggestions | theme / photo_spots / practical_notes / backup_plan / why_this 均未进入 Prompt 要求 |
| V4 | 槽位已铺、生成侧空转 | Python `DailyPlan`（`travel-agent-python/app/schemas/trip.py:129-137`）、Java `AgentGenerateResponse.DailyPlan`（经 metadataJson 落库）、前端 day-note 渲染（`TripDetailView.vue:155-159`）均已就绪 | 生成 JSON 不吐 → 全链路永远空；且 `why_this` 在 Java 侧 grep 无命中，连槽位都未铺 |
| V5 | requirements 静默截断 | `text[:500]`（`travel-agent-python/app/agent/generators.py:185`） | 主题简报 / 作品设定 / 禁忌清单易被砍半 |
| V6 | 讲解层过薄 | 管家 ≤250 字、3–4 段（`travel-agent-python/app/agent/butler.py:24`）；景点介绍 60–90 字百科腔（`:52`） | 与「预算拆解 + 选址逻辑 + 拍照清单」所需篇幅不匹配 |
| V7 | 海外短板放大不完整感 | 海外无坐标、地图隐藏；京都 16 项待复核的溯源噪音 | 可信机制在海外场景反而削弱信任 |

**断层链式结构**（读法）：七条断层不是并列的七个 bug，而是一条断裂的意图管线——

- **V1（进不来）**：意图在前端被降维成 6 个枚举标签，自由文本沦为可选补充；
- **V2（查不到）**：研究层契约里根本没有主题字段，检索围绕类目而非作品 / 兴趣 / 事件；
- **V3（不要求）**：生成 Prompt 只奖励「规范景点列表」，叙事字段不在输出契约中；
- **V4（吐不出）**：下游 Schema / 落库 / 渲染全部就绪却永远等不到内容——工程投资已付出，价值卡在最上游一环；
- **V5 / V6（次级瓶颈）**：即使打通上述链路，输入被 `[:500]` 截断、讲解被 250 / 60–90 字篇幅封顶，叙事密度仍然上不去；
- **V7（放大器）**：海外无坐标 + 溯源噪音（京都 16 项待复核），把上述所有单薄进一步放大为「不完整感」。

这条链解释了为什么价值升级必须以「全量重构」立项：只修任何单环（只改前端输入、或只改 Prompt），管线仍断在别处。

**定位张力**（承档案 §1.3）：

| 现有第一性叙事 | 用户当次比较维度 |
|----------------|------------------|
| 防幻觉、引用落地、可溯源、可降级 | 是否「懂我的主题」、是否「能直接照着走」 |

结论：可信骨架真实且健壮，但在兴趣巡礼 / 深度定制场景中价值感知弱。重构方向不是放弃可信，而是在可信骨架上把「意图理解 + 主题叙事 + 操作细节」做成一等输出。
**对应主题**：AD1（意图贯通）、AD5（Agent 能力升级）。

### 1.2 Python Agent：生成智能层的架构债

| # | 问题 | 证据 | 影响 |
|---|------|------|------|
| P1 | 无流式输出：`llm_client.py` 已有 `stream_chat` 但全部 API 同步 JSON 返回，路由为阻塞 `def` | `travel-agent-python/app/api/agent.py`、`app/common/llm_client.py` | 3–15 分钟生成期间用户零进度反馈；流式能力存在但闲置 |
| P2 | 契约松散：butler-note / poi-intros / poi-nearby / city-guide 端点裸 dict、无 Pydantic 校验；`DailyPlan.mini_route / backup_plan / photo_spots` 为无 schema 的 `list[dict]` | `travel-agent-python/app/api/agent.py`、`app/schemas/trip.py:129-137` | 字段变更无校验期防护，坏数据静默穿透到 Java / 前端 |
| P3 | Prompt 冗长重复：两段巨型 f-string 硬编码中文规则近乎复制 | `travel-agent-python/app/agent/day_stream.py:88`（`_llm_open_day`）、`:183`（`_llm_open_trip`） | 修一处漏一处，维护漂移；无法按 intent 差异化注入 |
| P4 | JSON 解析脆弱：多处 `_parse_json` 用正则截取 \`\`\`json 块 | `travel-agent-python/app/agent/` 内多处 | 模型输出轻微越界即解析失败，触发降级或浪费重试 |
| P5 | 兼容层堆积：`build_graph` 死代码、`day_workflow` 空壳、`agent_graph=None`、循环导入靠延迟 import | `travel-agent-python/app/agent/workflow.py`、`day_workflow.py`、`trip_graph.py` | 代码路径不可预测，排查成本高，重构干扰项多 |
| P6 | 错误静默降级：butler / poi_intros 大量 bare except 降级返回空 | `travel-agent-python/app/agent/butler.py` | 故障不可见：讲解为空时无从分辨是失败还是没内容 |
| P7 | 同步 I/O：httpx 同步客户端 + 线程池，uvicorn 单 worker；路线 / RAG 缓存进程内不共享，LLM 结果无缓存 | `travel-agent-python` 部署形态与各 client | 吞吐上限低；多实例部署即缓存 / 观测割裂 |
| P8 | 状态松散：`UnifiedAgentState` TypedDict 全程 dict 传递，节点间字段契约靠约定；`format_output` 300+ 行巨函数 | `travel-agent-python/app/agent/trip_graph.py:38`、`app/agent/workflow.py:576` | 加字段（如 intent / why_this）需全链路人工核对，漏传即空转 |
| P9 | 配置漂移：`.env.example` 与 `config.py` 默认值不一致 | `MAX_LLM_CALLS` 8 vs 32、`LIVE_PRICE_SEARCH` false vs true | 部署环境行为不可预期，联调排查成本被浪费 |
| P10 | 观测单机：指标 / trace 进程内 + jsonl 文件 | 进程内聚合 + jsonl 落盘 | 多实例不可聚合，无法回答「这次生成为什么慢 / 为什么降级」 |

**重点剖析**（为什么是架构债而非孤立 bug）：

- **P1 能力与使用的错位**：`stream_chat` 已存在于 `llm_client.py`，证明流式并非技术不可行，而是 API 层与 Java 调用方全部按「同步 JSON 一次性返回」设计。
  这决定了 AD2 流式改造的主战场在契约与编排层，而非 LLM 客户端层——客户端只差接线，端点与调用链才要重造。
- **P2 契约失守的连锁**：裸 dict 端点意味着 Python 侧任何字段演进（如新增 `why_this`）都不会在本地报错，错误要到 Java 反序列化或前端渲染时才以「静默为空」显形。
  V4 槽位空转长期无人察觉，正是这条失守链的直接后果；AD3 的 Pydantic 化清单（§4.4）首先收编这四个端点。
- **P3 双 Prompt 副本**：两段巨型 f-string 近乎复制，任何规则调整（如档案 P0-2 的叙事字段硬约束）都需双处同步；历史上大概率已发生过单边修改，未来也必然再发生。
  这是 AD4「Prompt 模板集中管理」的直接动机：模板化后 day / trip 两模式共享规则库，按模式差异注入变量。
- **P8 状态松散与 V4 同构**：`intent` / `why_this` 等新字段要贯通 Agent，需穿过 research → generate → reflect → format 全部节点；在约定式 TypedDict 传递下，任一节点漏读 / 漏写一个 key 就是又一次静默空转。
  V4 是该病灶的跨端版本，P8 是它的 Agent 内部版本——两处必须用同一套结构化方案（AD4）一起治。

**现状事实基线**（供后文阅读）：

- LangGraph 单图 `unified_agent_graph`（`travel-agent-python/app/agent/trip_graph.py:279`）按 `mode=day/trip` 分流，单图承载双模式；
- 反思校验 `validate_plans`（`travel-agent-python/app/agent/reflect.py:108`）检查时间冲突 / 可达性 / 饱和度 / 存在性；
- 工具注册 `tool_registry.py` 共 4 只读工具；LLM 为 DashScope qwen-plus / qwen-turbo。

**对应主题**：AD2（P1 / P7）、AD3（P2 / P4 / P9 配置契约化）、AD4（P3 / P5 / P8）；P6 由 AD2（降级事件显式推送）与 AD3（契约化后错误可见）共同消解，P10 由观测选型（§3.5）承接。

### 1.3 Java 后端：编排与状态机的失序

| # | 问题 | 证据 | 影响 |
|---|------|------|------|
| J1 | Planner 职责过重：单文件 477 行，`planDays`（:73-152）及其编排链 `generateWholeTrip` / `generateAndPersistDay` / `enrichItinerary` 等混居一处——编排 + 锁 + 幂等 + 富化 + 建议池 + 恢复标记六类职责混杂；`verifyAction` 在 Planner 与 DayPersistenceService 双份实现 | `travel-backend-java` `ItineraryAsyncPlanner` | 单点改不动：任何需求都要在近 480 行单文件里穿针引线；双实现必然漂移 |
| J2 | 轮询契约：生成进度靠前端 2.5s 轮询 `GET /{id}`；每天完成即 `evictCache` 清空整个 `itinerary:detail` 缓存（allEntries），detail 每次全量重建 | `ItineraryAsyncPlanner` 与 detail 缓存策略 | 轮询风暴 + 缓存形同虚设，读放大随行程数增长 |
| J3 | 状态机用文案承载状态：`planNote` 内嵌 `RESUME_MARKER` 字符串；main.status + day 5 态 + 恢复启发式（updatedAt 5min）叠加 | `ItineraryStatusRecovery` | 竞态窗口多，状态推断靠猜，恢复路径难测试 |
| J4 | 透传层冗余无类型：clarify / city-guide / poi-nearby 纯透传 `Map<String,Object>` / `JsonNode`；预算钳制、季节因子 Java / Python 双份维护 | 对应 Controller / Service | 契约三层失守的 Java 环节；业务规则双份漂移 |
| J5 | 事务边界：`persist` 的 @Transactional 内含全行程预算重算（delete + insert budget_detail） | `ItineraryDayPersistenceService.persist` | 事务放大：单日落库锁全行程，失败回滚代价大 |
| J6 | N+1 写：poiIntros 逐条 `updateById`；富化用公共 ForkJoinPool 无背压 | poiIntros 富化链路 | 富化慢且可能饿死公共池，DB 往返多 |
| J7 | AmapController 臃肿 ~460 行：图片代理 / 多源照片解析 / LRU 缓存内嵌 Controller | `AmapController` | Controller 承担服务层职责，无法复用与测试 |
| J8 | 单日 / 多日双生成路径：多日一次调 `/v1/generate`（读超时 180s），单日走 plan-context + generate-day 逐日，建议池来源不同 | `ItineraryAsyncPlanner` 双路径 | 同一产品两套行为，功能与修复都要做两遍 |
| J9 | 杂项：login 经 `AuthSessionHolder` ThreadLocal 隐式传 token；每个 Controller 方法 `currentUserId()` 都查一次库 | 认证链路与 Controller 基类 | 隐式依赖 + 每请求冗余 DB 查询 |

**重点剖析**：

- **J1 编排中枢过载**：`ItineraryAsyncPlanner` 477 行单文件内，`planDays`（:73-152）与其直接编排链（`generateWholeTrip` / `generateAndPersistDay` / `enrichItinerary` 等 10+ 私有方法）共同承担流程编排、分布式锁、幂等判重、结果富化、建议池管理、恢复标记写入六类职责——每类职责有独立的演化节奏，揉在同一文件意味着任何需求都要在近 480 行里穿针引线。
  `verifyAction` 在 Planner 与 DayPersistenceService 双份实现，则是「改 A 忘 B」的事故预埋；AD6 拆分 Planner 的第一刀就是把这六类职责还给各自的模块。
- **J2 轮询 + 全量 evict 的双重浪费**：前端 2.5s 轮询把进度感知成本全数转嫁给读路径；每天完成即 `evictCache`（allEntries）又让其余各天的 detail 缓存陪葬。
  缓存全量失效与正确性无关、纯属实现妥协——行程越长读放大越严重，这是 AD2（事件推送）与 AD6（精确缓存失效）必须联手的典型场景。
- **J3 状态三处叠加**：main.status、day 5 态、恢复启发式（updatedAt 5min 内视为进行中）互不知晓，再叠加 `RESUME_MARKER` 文案嵌入 `planNote`——恢复语义靠启发式「猜」。
  状态机的合法迁移路径无法穷举测试，竞态窗口只能靠撞见；AD6 显式状态机的靶心即在于此。
- **J8 双路径是隐性产品缺陷**：同一用户在「整行程生成」与「单日重生成」两条路径下拿到不同建议池、不同超时预算（180s 整程 vs 逐日）、不同失败恢复行为。
  用户感知到的任何「行为不一致」最终都要靠双倍维护成本兜底；AD8 的唯一目标就是消灭这组分叉。

**现状事实基线**：Spring Boot 3.2.5 / Java 17 / MyBatis-Plus / Redis / jjwt / Thymeleaf PDF；`ItineraryServiceImpl` 门面 + 8 子服务；幂等三层（Redis SETNX 日锁 `gen:day:{id}:{dayNo}` TTL 5min、`generation_action_id` 409、fingerprint SHA-256 409）；`AgentServiceImpl` RestClient connect 3s / read 180s、不重试防双计费；核心表 `itinerary_main / itinerary_day(metadataJson) / itinerary_item(溯源五字段) / itinerary_version(snapshotJson) / poi_knowledge / hotel_room_type / city_consumption / budget_detail / itinerary_chat_message / sys_user / user_preference / export_task`；`AgentGenerateResponse.DailyPlan` 已含 note / theme / miniRoute / backupPlan / photoSpots / practicalNotes 并经 metadataJson 落库（**唯 `whyThis` 在 Java 侧 grep 无命中**）。

**对应主题**：AD6（J1 / J3 / J5–J7 / J9）、AD2 + AD6（J2）、AD3 + AD6（J4）、AD8（J8）。

### 1.5 跨端系统性断层

前四节 36 条问题背后，是六条贯穿三端的系统性断层——它们是本次以「全量重构」而非局部修补立项的依据：

- **S1 全链路无事件推送通道，轮询 / 阻塞无处不在**
  表现：前端三处等待（`TripDetailView.vue:762-786,1322-1353,560-616`）+ Java 侧每天完成即 `evictCache` 全量清缓存（J2）。
  根因：三端之间只有「请求-响应 + 轮询数据库 / 缓存」一种对话方式；生成、导出、编辑三类等待在三端各自为政，没有任何共享的进度语义。→ AD2
- **S2 契约三层失守**
  表现：Python 裸 dict（P2）→ Java `Map<String,Object>` / `JsonNode` 透传（J4）→ 前端 `any[]`（F5）。
  后果：任何一处字段变更都无法在校验期发现，错误以「静默为空」而非报错的形式显形；叙事字段空转（V4）正是这种失守的必然产物。→ AD3
- **S3 同一业务规则双份维护**
  表现：预算钳制、季节因子在 Java / Python 双份实现（J4）；`verifyAction` 在 Planner 与 DayPersistenceService 双份（J1）。
  后果：行为漂移只是时间问题，且漂移总是先被用户而不是开发者发现。→ AD3 / AD6
- **S4 单日 / 多日双生成路径造成行为分叉**
  表现：多日一次调 `/v1/generate`（读超时 180s），单日走 plan-context + generate-day 逐日，建议池来源不同（J8）。
  后果：同一产品两套行为、两套故障模式，任何生成侧改进（如 AD5 叙事字段）都要验证两遍。→ AD8
- **S5 叙事字段「槽位已铺、内容空转」断层**
  表现：Schema / 落库 / 前端渲染全部就绪（V4），唯独生成契约（V3）与研究输入（V2）不产内容。
  后果：工程投资已付出、回报为零——这是三端协同失效中最昂贵的一种：每个环节单看都「没做错」，合起来却交付不了价值。→ AD1 / AD5
- **S6 可信骨架健壮但价值感知弱**
  表现：溯源五字段 / 引用落地 / 降级路径健壮，但同题对照在主题定制化 / 信息密度 / 操作细节上输给通用助手（§1.1 对照表）。
  后果：用户比较的是「懂不懂我」，不是「可不可信」——可信是必要条件而非充分卖点，必须叠加意图感知才能形成差异化。→ AD1 / AD5

#### 2.1.2 四大基调

所有架构决策（AD1–AD8）与第 3–5 章设计均须从这四条基调推导；与基调冲突的设计一律退回。

**① 意图驱动端到端**
- **是什么**：`intent` 是贯穿「前端主输入 → Java 透传 → Python 研究 / 生成 / 讲解」的一等字段，而非可选补充；偏好标签降为辅助信号。
- **为什么**：§1.1 已证明价值卡点不在模型而在管线——V1 进不来、V2 查不到、V3 不要求、V4 吐不出，任何单环修补无效（断层链式结构）。
- **约束什么**：任何新端点、新 Schema、新 Prompt 不得只接收 `preferences` 枚举而无 `intent` 通道；`intent` 进入 Prompt 必须定界符包裹（原则 5，§0.4 已声明）。

**② 流式优先**
- **是什么**：长耗时动作（生成 / 编辑 / 导出）默认走事件流（SSE），请求-响应仅用于瞬时操作；`llm_client.py` 的 `stream_chat` 能力从闲置转为主路径。
- **为什么**：3–15 分钟零反馈是当前体验最重的单项债务（P1 / F2 / S1），且逐日推送是前端逐日渲染、细粒度失败恢复的前提。
- **约束什么**：每条 SSE 通道必须有降级回轮询路径；降级本身作为 `degraded` 事件如实推送（原则 4 的工程化）。

**③ 契约先行**
- **是什么**：Python 全端点 Pydantic 化 → Java 强类型 DTO → 前端 TS 类型，三层契约同源同步；主契约新增字段五处联动（§4.4 核对表）。
- **为什么**：V4（槽位空转）证明了「无契约的槽位是负资产」——工程付费、价值为零、无人察觉（S2 三层失守的必然产物）。
- **约束什么**：禁止新增裸 dict 端点、`Map<String,Object>` 透传与 `any` 类型；主契约字段变更必须三层同 PR 落地。

**④ 可信骨架不破**
- **是什么**：溯源五字段、引用落地、诚实降级、防注入机制在重构中原样保留，并借契约校验与事件化降级显式增强。
- **为什么**：可信是项目立身之本（§0.4）；同题对照落败（S6）的正确解法是「可信 × 意图」相乘，不是用叙事冒充事实。
- **约束什么**：叙事字段（`why_this` 等）一律 `value_kind=generated`，不得影响 `verification_status`；开放模式 `unverified / before_departure` 标注不变；LLM 失败仍返回待研究草案。

### 2.3 架构决策清单 AD1–AD8

每条 AD 统一模板：**动机**（问题编号）→ **方案**（组件 / 文件级改动方向）→ **代价** → **五原则兼容性**。五原则缩写：①LLM-only、②引用落地、③诚实标注、④降级如实、⑤防注入。

#### AD1 意图（intent）一等公民端到端贯通

- **动机**：V1（前端 6 枚举标签降维）、V2（`ResearchTask` 无主题）、V5（`text[:500]` 截断）、F10（意图二等公民）、S5 / S6（槽位空转、价值感知弱）。
- **方案**：
  - 前端：`GenerateView.vue` 新增 `intent` 主输入（自然语言大文本框 + 示例 chips），偏好标签降为辅助信号，提交体携带 `intent`（交互设计见 §5）。
  - Java：`dto/GenerateRequest.java` / `AgentGenerateRequest.java` 增 `intent`（可选；无 `intent` 时以 `intent = requirements` 兜底）；编排器透传至 Agent 全部生成调用，butler-note / poi-intros payload 同步携带。
  - Python：`app/schemas/trip.py` 的 `GenerateRequest` / `GenerateDayRequest` 增 `intent: str | None`（≤800 字）；`app/agent/generators.py` 的 `_requirements_clause` 拆分为 `_intent_clause`（注入位置更靠前、权重更高）+ `_requirements_clause`；`requirements` 上限 2000→4000、截断阈值 ≥1500（字段定义见 §4.1）。
  - 意图提炼：新增轻量 `distill_intent(city, intent, preferences, requirements) -> IntentBrief`（`theme_label / must_include / avoid / tone / logistics`，qwen-turbo 单次调用），**失败降级为原样透传用户文本**，不阻断生成。
  - 研究层：`ResearchTask` 增 `intent / intent_keywords`（详见 AD5）。
- **代价**：三层 Schema 同步改动（靠 AD3 核对表防漏）；`distill_intent` 每次生成增加一次轻量 LLM 调用（约 +1–3s，qwen-turbo 成本可忽略且有降级路径）；`intent` 扩大 Prompt 注入面，防注入处理见兼容性。
- **五原则兼容性**：兼容。① `intent` 只作生成指令输入，内容仍 100% LLM 生成；② 不触碰 refs / 溯源机制；⑤ `intent` 与 `requirements` 同样以定界符包裹 +「数据非指令」声明进入 Prompt（§0.4 原则 5 对新字段的既有要求）；④ 提炼失败降级原样透传并如实标注，不伪造意图。

#### AD2 SSE 流式替代三处轮询

- **动机**：P1（`stream_chat` 闲置、路由阻塞）、P6（bare except 静默降级不可见）、P7（同步 I/O 单 worker，事件化倒逼 async 化）、J2（轮询 + 全量 evict）、F2（三处轮询 / 长阻塞）、S1（全链路无事件通道）。
- **方案**：
  - 技术链路：Python Agent 节点完成（研究 / 逐日 / 管家 / 降级）→ 发布事件到 Redis pub/sub topic `gen:events:{itineraryId}` → Java SSE 网关订阅并经 SseEmitter 推送前端；多实例部署天然就绪（任一 Java 实例订阅同一 topic 即可转发）。
  - 覆盖三类等待（F2 的三份等待逻辑收敛为一份）：生成进度（`research_start / research_done / day_start / day_done / butler_note / degraded / complete`）、chat 流式回复（替代 70s 长阻塞）、导出完成通知（替代 1.5s×60 轮询）。
  - 协议与重连：统一信封 `{type, itineraryId, seq, ts, data}`，`seq` 单调递增；心跳 15s；断线降级回轮询——现有 `GET /{id}` 保留为兼容路径，重连失败即回退一次全量 GET 对账（协议详见 §4.3）。
  - 缓存联动：`day_done` 事件触发单 itinerary 精确缓存失效（配合 AD6），替代每天完成 `evictCache` allEntries。
- **代价**：三端各需实现事件语义（Python 发布、Java 转发、前端消费），为本次重构最大单项工作量之一；SseEmitter 连接管理（超时 / 心跳 / 连接数上限）与反向代理 SSE 兼容性（`X-Accel-Buffering: no` 等）需部署确认；Redis pub/sub 消息不持久，故选择「重连即全量对账」而非消息回放，换取实现简单（§4.3.4）。
- **五原则兼容性**：兼容且显式增强。④ 降级从 bare except 静默吞掉（P6）改为 `degraded` 事件如实推送——本 AD 是原则 4 的工程化落地；①②③ 不涉及：事件只承载进度与摘要，不拼装行程内容，推送的 day 摘要来自已生成并校验的数据。

#### AD3 契约先行

- **动机**：P2（裸 dict 端点 + `list[dict]` 字段）、P4（`_parse_json` 正则脆弱）、P6（契约化后错误可见）、P9（`.env.example` 漂移）、V4（槽位空转无人察觉）、J4（`Map/JsonNode` 透传）、F5（`any[]` 逃逸）、S2（三层失守）、S3（规则双份）。
- **方案**：
  - Python：`/v1/butler-note`、`/v1/poi-intros`、`/v1/poi-nearby`、`/v1/city-guide` 四端点从裸 dict → Pydantic 请求 / 响应模型（§4.4 清单）；`DailyPlan` 的 `mini_route / backup_plan / photo_spots` 从松散 `list[dict]` → 结构化子模型（§4.1）；LLM 输出改 `response_format json_object` + Pydantic 校验 + 单次修复重试（配合 AD4，替代正则截取）；`.env.example` 与 `config.py` 默认值对齐纳入 CI 检查（治 P9）。
  - Java：clarify / city-guide / poi-nearby 透传从 `Map<String,Object>` / `JsonNode` → 强类型 DTO；对齐 wire 规范（ApiResponse 信封 + camelCase 别名 + `X-Agent-Token / X-Request-ID / X-Agent-Run-ID`）；预算钳制、季节因子等双份规则（S3）收敛到单一权威端（生成侧 Python 权威，Java 仅做展示层计算）。
  - 前端：`types/itinerary.ts` 补 `whyThis` / `dayOptions` 等；消灭 `draftPlans: any[]` 等类型逃逸点（配合 AD7）。
  - 同源维护规范：生成主契约每新增字段，必须同时落地五处——Pydantic 模型、Java VO、落库映射、TS 类型、前端渲染；以单测断言五处字段存在，缺一 CI 失败（§4.4.4 核对表，防 V4 复发）。
- **代价**：接口改造触及三端全部边界代码；契约收紧后，过去静默穿透的坏数据开始显式报错，短期错误处理代码增加（这是收益而非成本，但需接受）；规则收敛（S3）涉及行为对齐回归。
- **五原则兼容性**：兼容，且是原则 ②③④ 的防护网——契约校验让「未标注 unverified」「降级数据冒充正常」在校验期而非用户侧显形；⑤ 契约中的用户输入字段同样纳入定界符包裹范围。

#### AD4 LangGraph 状态结构化 + Prompt 模板集中

- **动机**：P3（双巨型 f-string 复制漂移）、P5（`build_graph` 死代码 / `day_workflow` 空壳 / 延迟 import）、P8（TypedDict 松散 + `format_output` 300+ 行）。
- **方案**：
  - 状态：`UnifiedAgentState`（`app/agent/trip_graph.py:38`）从 TypedDict → Pydantic State；`intent / why_this` 等新字段的贯通从「全链路人工核对」（P8 与 V4 同构）变为「Schema 缺字段即报错」。
  - Prompt：`day_stream.py` 两段巨型 f-string（`_llm_open_day:88` / `_llm_open_trip:183`）拆到 `app/prompts/` 模板模块——版本常量 + day / trip 共用片段（规则库、引用规范、防注入声明）继承 + 模式差异片段注入；模板变更记版本号，评测集固定 prompt 版本（承档案 §8.3）。
  - 输出：LLM 调用统一 JSON 约束（`response_format json_object`）+ Pydantic 校验，失败携带校验错误重试一次，再失败走降级（治 P4 正则脆弱）。
  - 清理：删除 `workflow.py` 死代码、`day_workflow.py` 空壳、循环导入延迟 import（P5）；`format_output` 拆分为按域的格式化函数。
- **代价**：状态模型重构需全图回归（research → generate → reflect → format 全节点）；模板模块引入间接层，调试时需定位到具体模板版本；结构化输出重试增加最坏情况耗时（+1 次 LLM 调用）。
- **五原则兼容性**：兼容。① 模板重组不改内容来源；② 引用规范（`[R1..Rn]` 要求）作为共用片段集中维护，更不易漂移；③④ 防注入声明、降级文案纳入共用片段，杜绝「改一处忘一处」；⑤ 定界符包裹逻辑在模板层单点实现。

#### AD5 Agent 能力升级

- **动机**：V2（研究不知主题）、V3（生成契约无叙事字段）、V4（槽位空转）、V6（讲解过薄）、V7（海外短板放大）、S5 / S6。
- **方案**：
  - 生成契约补齐（`_llm_open_day` / `_llm_open_trip` 的 JSON 契约 + Prompt 硬约束，字段定义见 §4.1）：顶层 `trip_theme`；日级 `theme`（叙事句硬约束）、`photo_spots{name, tip, best_time}`（0–4）、`practical_notes`（2–4 条每日必填）、`backup_plan{if, action}`、`day_options{label, summary, tradeoff}`（0–2 组）；item 级 `why_this`（attraction 必填，无主题时写口碑 / 地理 / 节奏理由）。
  - 研究层主题词：`ResearchTask` 增 `intent / intent_keywords`（从 `intent` 抽 3–8 个检索词：作品名 / 原型地 / 活动名）；`factory._run_search` 的 `extra_keywords` 合并 `intent_keywords`，web 补池 query 拼 `city + keyword`；评估器证据充分性增加「意图关键点位类型覆盖」维度（承档案 §5.4）。
  - 讲解扩写（`app/agent/butler.py`）：管家 ≤250 字 → **400–600 字四段结构**（意图如何贯穿全程 / 酒店选址与意图的关系 / 预算怎么花哪里可省 / 出发前 1–2 条必做），输入带 `intent` + 实际 plans；点位介绍 60–90 字 → **80–140 字** + 与本趟意图的一句连接。
  - 海外（V7，运维项随 §6 里程碑承接）：配置 `GOOGLE_MAPS_API_KEY` 恢复坐标与地图；无 key 时如实文案「叙事行程已生成；配置 Google 后恢复地图与附近推荐」（承档案 §5.7），不伪造距离。
- **代价**：Token 消耗与单日生成耗时上升（叙事字段约占输出增量 30–50%），需按天上调 max_tokens 并为叙事字段设字数上限（`why_this` ≤120 字、notes ≤4 条）防 JSON 截断（承档案 §10）；无主题输入时可能输出啰嗦——约定无 `intent` 时 `photo_spots / day_options` 可选输出；输出稳定性依赖 AD4 的校验重试兜底。
- **五原则兼容性**：兼容。① 叙事内容仍 100% LLM 生成，研究只作证据；② `why_this` 等叙事字段 `value_kind=generated`，与事实字段（坐标 / 票价 / 核验状态）分层，不因写得像实锤就标 `verified`（承档案 §5.2 诚实性边界）；③ 开放模式标注不变；④ 叙事字段生成失败不影响骨架交付，缺省即空、不拼装；⑤ `intent_keywords` 进入检索 query 前同样定界符处理。

#### AD6 Java 编排层重划

- **动机**：J1（Planner ~480 行六类职责混杂 + verifyAction 双份）、J2（全量 evict）、J3（RESUME_MARKER 文案状态机）、J4（透传无类型）、J5（事务内预算重算）、J6（N+1 + 公共池无背压）、J7（AmapController ~460 行）、J9（ThreadLocal 隐式 token）、S3。
- **方案**：
  - Planner 拆分（治 J1，六类职责各归其位）：`ItineraryAsyncPlanner.planDays` 拆为——**编排器**（纯流程：逐日调度、事件发布、状态迁移，建议池管理并入）、**幂等门**（Redis SETNX 日锁 `gen:day:{id}:{dayNo}` + `generation_action_id` + fingerprint 三层判重，`verifyAction` 双份实现合并为单一服务）、**富化器**（butler-note / poi-intros 调用与写回，独立线程池 + 有界队列背压，替代公共 ForkJoinPool）。
  - 显式状态机（治 J3）：`itinerary_main` 增生成状态枚举字段（如 `GENERATING / PARTIAL / COMPLETED / FAILED`）+ 阶段时间戳，替代 `planNote` 内嵌 `RESUME_MARKER` 文案与 updatedAt 5min 启发式；`ItineraryStatusRecovery` 依据显式状态恢复，合法迁移路径可穷举测试。
  - 缓存精确失效（治 J2，配合 AD2）：`itinerary:detail` 从每天完成 `evictCache` allEntries → 单 key（`itinerary:detail:{id}`）按 `day_done` 事件失效。
  - 事务边界（治 J5）：`ItineraryDayPersistenceService.persist` 的 @Transactional 收窄为当日数据写入；全行程预算重算（delete + insert budget_detail）移出事务，改为落库成功后异步重算。
  - 写入与杂项（治 J6 / J7 / J9）：poiIntros 逐条 `updateById` → 批量写；`AmapController` 的图片代理 / 多源照片解析 / LRU 缓存拆为独立服务；`currentUserId()` 每请求冗余查库收敛到请求上下文一次解析。
- **代价**：本次重构回归面最大的单项（9 条 J 类问题交汇）；状态机显式化需存量数据迁移（历史 RESUME_MARKER 文案 → 状态字段的回填脚本）；拆分期间须保持对外 API 与行为不变（重构行为不变式）。
- **五原则兼容性**：兼容。本 AD 纯编排层治理，不触内容生成与溯源链路；④ 显式状态机反而让「部分成功 / 已降级」状态如实可查（现状靠文案猜）。

#### AD7 前端组件化重构

- **动机**：F1（2181 行巨石 + ~800 行样式）、F3（1 store + 手工同步 10+ 处）、F4（全量引入 + 1.4MB 封面）、F5（`any[]` 逃逸）、F6（样式重复 + !important）、F7（可访问性）、F8（`api/index.ts` 混编 + 死代码 + 硬编码城市表）、F9（封面映射重复）。
- **方案**：
  - 组件拆分（治 F1 / F6）：`TripDetailView.vue` 按职责拆为 `day-list`（逐日卡片 + 叙事区）、`chat-panel`（NL 编辑聊天）、`discover`（附近推荐 / 城市 guide）、`export`（导出任务）、`hotel-panel` 等子组件，scoped 样式随组件分域。
  - 状态层（治 F3）：新增 itinerary Pinia store——`detail` 单一数据源、`revision` 乐观锁、聊天草稿乐观更新，消灭 10+ 处手工同步；`useItineraryStream` composable 封装 SSE 订阅、事件分发、断线自动降级回轮询（AD2 的前端侧）。
  - 工程卫生（治 F4 / F8 / F9）：`api/index.ts`（459 行 45+ 函数）拆为按域模块（generate / detail / chat / export / discover），类型独立到 `types/`；`BaseMap.vue` 死代码删除、`geo.ts` 硬编码城市 / 省份表收敛到单一常量源、`CITY_COVERS` 与 `DESTINATIONS` 两处封面映射合一；EP / echarts 按需引入 + 封面压缩与懒加载（详见 §3.2 与 §5.6）；可访问性修正（嵌套 role、聊天区列表语义，治 F7）。
- **代价**：前端工作量最大的单项（9 条 F 类问题）；拆分期间新旧组件并存需保持路由与功能可用；store 化改动全部状态流，需以既有交互（拖拽 / NL 编辑 / 酒店替换）回归为准。
- **五原则兼容性**：兼容。纯展示与状态层重构；溯源标签、降级提示的渲染随子组件迁移并保持原语义（§5 设计将强化而非弱化其可见性）。

#### AD8 单日 / 多日双生成路径统一

- **动机**：J8（多日一次调 `/v1/generate` 读超时 180s vs 单日 plan-context + generate-day 逐日，建议池来源不同）、S4（同一产品两套行为与故障模式）。
- **方案**：**推荐彻底统一为逐日生成流**——多日生成 = 研究阶段一次完成后，逐日复用单日生成路径（plan-context + generate-day），多日一次性 `/v1/generate` 退出主路径（端点保留兼容，见 §4.2）。理由：
  1. **SSE 逐日推送的天然前提**：统一后 `day_done` 事件与生成粒度一一对应，前端逐日渲染无需等待整程（AD2 依赖本决策）；
  2. **失败粒度更细**：单日失败重试当日（幂等门已有 `gen:day:{id}:{dayNo}` 日锁语义），替代整程 180s 超时后全量失败；
  3. **幂等与行为语义一致**：一套超时预算、一套建议池、一套恢复路径，治 S4 的「双倍维护」。
- **代价**：LLM 调用次数与总耗时变化需评估——研究层证据跨日复用（研究仍一次完成），主要增量为每日一次请求往返与逐日上下文重建 token；若实测总耗时显著劣化，回退方案为保留整段生成作 fast-path（两路径并存但共享契约与事件协议），本方案将其列为备选而非推荐。
- **五原则兼容性**：兼容。生成路径合并不改内容来源与溯源；④ 逐日失败可以更诚实地标注「第 N 日待重试」而非整程失败。

**AD 依赖关系**（供第 6 章里程碑排期参考）：

| 依赖 | 说明 |
|------|------|
| AD1 → AD5 | 意图贯通是能力升级的输入：无 `intent` 通道，叙事契约与主题检索无从谈起 |
| AD3 横切 AD1 / AD5 | 每个新增字段须过五处核对表（§4.4.4）——契约先行是防 V4 复发的制度保障 |
| AD8 → AD2 | 逐日统一是 SSE 逐日推送的前提：事件粒度 = 生成粒度，双路径下 `day_done` 语义无法对齐 |
| AD2 ↔ AD6 | 事件发布挂接在编排器上、缓存精确失效依赖 `day_done` 事件——二者须同里程碑落地 |
| AD4 → AD5 | 叙事字段的输出稳定性依赖结构化输出 + 校验重试兜底 |
| AD7 可并行先行 | 前端组件化不阻塞后端，可与 AD1–AD6 并行；但 store 设计须预留 SSE 事件入口（`useItineraryStream`） |

### 2.4 端到端数据流

三条主链路叙事 + 时序表。事件类型与信封定义见 §4.3；本节只讲流。

#### 2.4.1 生成流

用户在 GenerateView 提交「`intent` + 偏好标签 + 预算 + 日期」，Java 建壳立即返回 `tripId`（不等待生成），前端跳转详情页并订阅 SSE。Java 编排器调用 Python 统一 Agent 图：`distill_intent` 轻量提炼（失败原样透传）→ 三域研究（景点 / 酒店 / 美食并行，携带 `intent_keywords`，`research_done` 携带证据规模与降级标记）→ 逐日生成（叙事契约：`theme / why_this / 细节字段`）→ reflect 校验（时间 / 可达 / 饱和 / 存在性）→ 逐日经 Java 幂等门落库（day 五态 + `metadataJson` 叙事字段 + item 溯源 + `why_note` 列）→ 每步事件经 Redis pub/sub → SseEmitter 推前端 → 前端逐日增量渲染（不再等整程）。全部日落库后：富化器调 butler-note（`intent` + 实际 plans，400–600 字四段）与 poi-intros → 版本快照 → `complete` 终态汇总（含 `degradedDays` 如实记录）。

| 步骤 | 执行方 | 事件或动作 |
|------|--------|------------|
| 1 | 前端 | `POST /api/itinerary/generate`（`intent` + 偏好 + 预算 + 日期） |
| 2 | Java | 建壳 `itinerary_main`（状态 `GENERATING`），立即返回 `tripId` |
| 3 | 前端 | 跳详情页，`GET /api/itinerary/{id}/events` 订阅 SSE |
| 4 | Java→Python | 编排器调用统一 Agent 图（`intent` 透传，幂等门判重） |
| 5 | Python | `distill_intent`（qwen-turbo；失败降级原样透传） |
| 6 | Python | 事件 `research_start` → 三域并行研究（`intent_keywords` 检索） |
| 7 | Python | 事件 `research_done`（证据规模 + 降级标记） |
| 8 | Python | 逐日：事件 `day_start(dayNo)` → 生成（叙事契约）→ reflect 校验 |
| 9 | Python→Java | 事件 `day_done(dayNo)`：Java 幂等门落库当日（事务收窄）+ 单 key 缓存精确失效 + 事件转发前端 |
| 10 | 前端 | 收 `day_done` → store 更新 → 当日卡片增量渲染 |
| 11 | Python | 任一环节降级 → 事件 `degraded`（scope / reason / fallback）如实推送 |
| 12 | Java | 富化器调 butler-note（`intent` + plans）→ 事件 `butler_note`；poi-intros 批量写 |
| 13 | Java | 版本快照（`snapshotJson` 含叙事字段）+ 状态 `COMPLETED` / `PARTIAL` + 事件 `complete` |

#### 2.4.2 编辑流

用户在 chat-panel 提交自然语言修改（如「第二天太赶，去掉一个点，加一个咖啡店」），走 `POST /{id}/chat-edit/stream` SSE 变体：Java 转发 Python `/v1/chat-turn`（携带行程上下文与 `intent`），LLM 回复流式逐段推前端；回复中的 `plans` 草稿以结构化变更建议呈现，用户点击「应用」后前端带 `baseRevision` 提交——Java 校验 revision 乐观锁（不匹配返回 409 提示刷新），匹配则落库变更 + 预算重算（persist 事务外）+ 版本快照 + revision 递增，前端 store 更新 `detail`。SSE 失败时回退原 70s 阻塞端点（降级路径保留）。

| 步骤 | 执行方 | 事件或动作 |
|------|--------|------------|
| 1 | 前端 | chat 输入 → `POST /api/itinerary/{id}/chat-edit/stream`（SSE） |
| 2 | Java | 转发 Python `/v1/chat-turn`（行程上下文 + `intent`） |
| 3 | Python | LLM 流式回复 → 事件 `chat_token` 逐段推送 |
| 4 | 前端 | 流式渲染回复；事件 `chat_draft` 携带 `plans` 草稿（变更摘要 + diff） |
| 5 | 前端 | 用户确认应用 → 提交 apply（`baseRevision`） |
| 6 | Java | revision 乐观锁校验：不匹配 → 409（提示刷新对账）；匹配 → 落库变更 |
| 7 | Java | 预算重算（persist 事务外）+ 版本快照 + revision 递增 |
| 8 | 前端 | store 更新 `detail`，乐观更新落地确认 |

#### 2.4.3 导出流

用户发起 PDF 导出，Java 创建 `export_task` 记录（状态 `PENDING`）并立即返回 `taskId`；异步渲染 PDF（Thymeleaf 模板已纳入 `theme / practicalNotes / why` 叙事字段）；完成后发布 `export_done` 事件——**复用同一 `events` SSE 通道**，前端收到事件即展示下载入口，替代现状 1.5s×60 轮询。SSE 断线期间自动降级回 export tasks 轮询接口对账。

| 步骤 | 执行方 | 事件或动作 |
|------|--------|------------|
| 1 | 前端 | `POST /api/itinerary/{id}/export` |
| 2 | Java | `export_task` 建记录（`PENDING`），返回 `taskId` |
| 3 | Java | 异步渲染 PDF（Thymeleaf，模板含叙事字段） |
| 4 | Java | 完成 → 状态 `DONE` + 事件 `export_done`（复用 `events` 通道） |
| 5 | 前端 | 收 `export_done` → 下载入口就绪（降级路径：轮询 export tasks） |

## 3. 技术栈选型

### 3.1 选型原则

- **最小代价换最大价值**：每项选型优先评估「收编问题数 ÷ 改造成本」；SSE 与契约化之所以立项，因为分别收编 6 条与 9 条问题（§1.6），而栈本身零更换。
- **不为重构而重构**：框架、语言、存储层全部保留——42 条问题无一需要换语言或换框架才能解决；换栈类提案默认否决（§3.6）。
- **保留可信骨架**：溯源、引用落地、降级、防注入相关的既有实现（Redis 锁、Pydantic、LangGraph 图结构、jjwt）原样保留，只做收编与增强。
- **渐进式可回退**：每项改造保留旧路径作降级（SSE 回轮询、流式编辑回阻塞端点、逐日统一回 fast-path），新路径稳定一个里程碑后才评估移除（节奏由第 6 章控制）。

**选型总览**（速查，明细见 3.2–3.5）：

| 层 | 保留 | 升级 | 引入 |
|----|------|------|------|
| 前端 | Vue3 + TS + Vite + Pinia + Element Plus + echarts + vuedraggable + axios | EP / echarts 按需引入；strict TS 类型收紧 | `@microsoft/fetch-event-source` |
| Java | Spring Boot 3.2.5 + MyBatis-Plus + RestClient + jjwt | —（靠设计重划 AD6，不靠换栈） | SseEmitter（servlet 栈内置）+ Redis pub/sub（现有 Redis 新用途） |
| Python | FastAPI + LangGraph + Pydantic v2 + SQLite 用量日志 | httpx.AsyncClient + 路由 async 化；LLM `json_object` 结构化输出 | 自建 `app/prompts/` 模板模块 |
| 基础设施 | MySQL + Redis + Chroma + 进程内观测 | `.env.example` 对齐 + CI 校验 | —（OTLP 为 P3 演进项） |

一句话总结：**全栈零更换、依赖净新增 1 个（fetch-event-source）、Redis 多一种用法**——所有结构性收益来自设计重划（AD1–AD8），不来自换技术。

### 3.2 前端

选型总策略：**栈零更换、工程治理 + 两处精准引入**——按需引入治 F4（包体积），`@microsoft/fetch-event-source` 承接 AD2 事件流，其余全部保留。

| 项目 | 现状 | 决策 | 理由 | 否决备选 |
|------|------|------|------|----------|
| 框架 | Vue 3.4.27 + TS 5.4.5 + Vite 5 | **保留** | F 类问题全部可通过组件化与工程治理解决，与框架无关 | 升 Vue 大版本 / 换 React：零问题编号收益，纯迁移成本 |
| UI 库 | Element Plus 2.7.6 全量引入 | **保留 + 按需引入**（`unplugin-vue-components` + `unplugin-auto-import`） | EP 覆盖现有全部场景（表单 / 表格 / 弹层 / 消息），生态成熟；按需引入直接治 F4 包体积 | Naive UI 等换库：现有 40+ 组件用法需重写、迁移收益低；视觉重设计（§5）靠设计令牌与定制主题实现，不依赖换库（§3.6③） |
| 图表 | echarts 6 全量 import | **保留 + 按需注册**（`echarts/core` + 按需组件） | 预算 / 统计图仅用少量图表类型，按需注册可减 60% 以上体积 | 换轻量图表库：重写全部图表配置，收益不明确 |
| SSE 客户端 | 无（axios 轮询，timeout 180s） | **引入 @microsoft/fetch-event-source** | 支持 POST + 自定义头（Bearer token）+ 断线重连 + 心跳控制，是 AD2 的标准件 | 原生 EventSource：仅 GET、无法带 Authorization 头；WebSocket：双向能力闲置，需额外连接管理 / 心跳 / 网关配置（§3.6④） |
| 状态 | Pinia（仅 user store） | **保留 + 扩展**（新增 itinerary store，AD7） | Pinia 已在栈内，F3 的解法是补 store 而非换方案 | — |
| 类型 | `types/` 分散 + `any[]` 逃逸（F5） | **收紧：strict TS + 契约类型独立到 `types/`** | AD3 前端侧；字段变更经类型检查显形 | 放宽 lint：与契约先行基调冲突 |
| 拖拽 | vuedraggable | **保留** | 日程拖拽编辑在用、稳定 | — |
| HTTP | axios（timeout 180s） | **保留**（控制流） | 请求-响应类调用维持 axios；事件流走 fetch-event-source，两者按流分工 | 全部换 fetch：无收益 |

**SSE 客户端接入要点**（AD2 前端侧的实施约束，由 `useItineraryStream` 统一封装）：

- 订阅用 POST + `Authorization` 头（fetch-event-source 能力，规避 EventSource 的 GET-only 限制）；
- 断线自动重连：指数退避，上限 30s；重连成功后立即执行一次全量 `GET /{id}` 对账（§4.3.4），不依赖事件回放；
- 重连连续失败达阈值（如 3 次）自动切换轮询模式并提示网络状态——现有 2.5s 轮询 + 连败 5 次熔断语义保留为降级实现；
- 事件流与控制流分工：axios 只做请求-响应，fetch-event-source 只消费 `text/event-stream`，不混用；SSE 稳定后 axios 的 180s 长超时随阻塞端点一并退役。

**按需引入实施注意**（治 F4 的构建细节，防「形按需、实全量」）：

- EP 组件解析器（`ElementPlusResolver`）须同步配置样式自动导入，否则组件按需、样式仍全量；
- echarts 按需注册集中在单一 `charts/` 模块，组件内禁止直接全量 import（lint 规则约束）；
- 封面图（6 张共 1.4MB JPG）转 WebP + 压缩 + 懒加载，目标单张 ≤200KB（视觉与性能细节见 §5.6）。

### 3.3 Java

选型总策略：**版本零升级、依赖零新增**——SSE 用 servlet 栈标准件 + 现有 Redis，J 类问题全部靠设计重划（AD6）解决，不靠换栈。

| 项目 | 现状 | 决策 | 理由 | 否决备选 |
|------|------|------|------|----------|
| 框架 | Spring Boot 3.2.5 / Java 17 | **保留** | J 类问题全部是设计问题（职责 / 状态机 / 事务），非版本问题 | 升级 3.3+：无所需特性；WebFlux 全响应式：SseEmitter 在 servlet 栈足够，全响应式重写成本与「推事件」目标完全不成比例（§3.6②） |
| SSE 服务端 | 无 | **引入 SseEmitter + Redis pub/sub** | Servlet 栈标准件；Redis pub/sub 复用现有实例且多实例天然就绪（任一实例订阅 topic 即可转发，AD2） | WebSocket/STOMP：双向闲置 + 额外连接管理；Kafka/RocketMQ 事件总线：单应用事件量级（单行程 <100 事件）过重 |
| ORM | MyBatis-Plus | **保留** | 现有映射稳定；J6 批量写用其 API 即可实现 | 换 JPA：大面积重写 mapper，零问题编号收益 |
| HTTP 客户端 | RestClient（connect 3s / read 180s，不重试） | **保留** | 「不重试防双计费」是有意设计；AD8 统一逐日后读超时按单日预算收窄 | WebClient：仅全响应式场景才需要 |
| 认证 | jjwt | **保留** | 功能完备；J9 是使用方式问题（ThreadLocal 隐式传递），非库问题 | Spring Authorization Server：过重 |
| 新增依赖 | — | **无** | 克制原则：本层所有问题用现有栈可解 | — |

**SseEmitter 实现要点**（AD2 Java 侧的实施约束）：

- 连接生命周期：建立时注册 emitter 池（itineraryId → emitters），`complete` / `timeout` / `onError` 时移除，防连接泄漏；
- 心跳：15s 定时发送注释行，防中间代理空闲断连；
- 多实例：SSE 网关订阅 Redis pub/sub（`psubscribe gen:events:*` 或按需 subscribe / unsubscribe），转发给本实例持有的 emitter，发布方无需感知实例拓扑；
- 连接治理：单用户并发连接数上限（如 3），超出返回 429 并提示复用既有连接；导出完成事件复用同一 `events` 通道，不为 PDF 单开连接。

### 3.4 Python

选型总策略：**框架全保留、I/O 模型升级、契约工具补全**——async 化治 P7，`json_object` + 校验重试治 P4，`prompts/` 模块治 P3。

| 项目 | 现状 | 决策 | 理由 | 否决备选 |
|------|------|------|------|----------|
| Web 框架 | FastAPI | **保留** | P 类问题无一是框架问题；SSE 响应与 Pydantic 契约均为 FastAPI 原生能力 | 换 Litestar/Flask：纯迁移成本 |
| Agent 编排 | LangGraph（单图 mode=day/trip 分流） | **保留** | 图结构成熟（research → generate → reflect → format），AD4 只重构 State 类型与 Prompt 来源 | 自研编排：零收益高风险（§3.6⑤） |
| 数据校验 | Pydantic v2（部分端点未用） | **保留 + 全端点覆盖** | AD3 主武器；v2 的 `model_validate` + JSON Schema 能力直接服务结构化输出 | msgspec：性能收益不显著、生态弱 |
| HTTP | httpx 同步客户端 + 线程池 | **升级为 httpx.AsyncClient + 路由 async 化** | 治 P7 同步 I/O 单 worker 上限；FastAPI 原生 async 释放三域研究 / 工具调用并发 | 线程池扩容：治标，事件循环阻塞依旧 |
| LLM 结构化输出 | 正则截取 ```json 块（P4） | **DashScope `response_format json_object`（qwen-plus 支持）+ Pydantic 校验 + 单次修复重试** | json_object 模型支持面稳；校验失败携带错误信息重试一次、再失败降级——修复率最高且失败模式可控 | `json_schema` 严格模式：DashScope 模型支持面不稳（复杂 schema 部分模型不支持），失败不可控 |
| Prompt 管理 | 巨型 f-string 硬编码（P3） | **自建轻量 `app/prompts/` 模块 + 版本常量** | 单文件模块即可完成片段继承 / 变量注入 / 版本化；评测集需固定 prompt 版本号（承档案 §8.3） | Langfuse / Prompty 等外部平台：引入部署 / 网络 / 密钥运维成本，本地模块够用；保留为未来多模型 A/B 的演进方向 |
| 用量日志 | SQLite | **保留** | 单机调试够用；P10 聚合问题由 OTLP 演进承接（§3.5） | 立即换 ClickHouse/Loki：过度设计 |

**结构化输出调用时序**（AD4「校验失败重试一次」的精确定义）：

1. 构造请求：system + user Prompt（`app/prompts/` 模板，版本常量注入）+ `response_format={"type": "json_object"}`；
2. 首次解析：`json.loads` → Pydantic `model_validate`；
3. 校验失败：将校验错误（字段路径 + 原因）拼入修复 Prompt 重试**一次**；
4. 再失败：走降级路径——当日返回待研究草案 + `degraded` 事件（原则 4），绝不拼装半成品；
5. 全程记录 prompt 版本号与重试次数入用量日志（与观测联动，回答「为什么慢 / 为什么降级」）。

### 3.5 基础设施

选型总策略：**存储层零更换、Redis 加一种用法（pub/sub）、观测做减法不做加法**。

| 项目 | 现状 | 决策 | 理由 | 否决备选 |
|------|------|------|------|----------|
| MySQL | 权威 POI 库（2142 条 / 6 城）+ 全部业务表 | **保留** | 权威数据层不动（可信骨架的一部分）；仅 `itinerary_main` 增状态字段、`itinerary_item` 增 `why_note` 列（§4.1） | 换 PostgreSQL：无所需特性，纯迁移风险 |
| Redis | 缓存 / 分布式锁 / 幂等 | **保留 + pub/sub 新用途** | 事件总线复用现有实例，零新增组件；SETNX 幂等锁原样保留 | Kafka / Redis Stream：事件量级远不需要持久化队列 |
| Chroma | bge-m3 向量 RAG | **保留** | 检索证据层不动；AD5 只改检索词来源（`intent_keywords`） | 换 Milvus/Qdrant：数据量不构成迁移理由 |
| 观测 | 进程内 metrics + jsonl（P10） | **保留 + 预留 OTLP 导出接口为 P3 演进项（不现在做）** | 单实例阶段够用；AD2 的 `degraded` 事件已把最关键的「为什么降级」变成显式数据 | 立即上 OTel Collector + Grafana：运维负担前置 |
| 配置 | `.env.example` 与 `config.py` 漂移（P9） | **对齐 + CI 校验**（默认值一致性检查入 CI） | 治 P9 部署行为不可预期 | — |

**观测演进路径**（P10 的处理时序，非现在做）：当前进程内 metrics + jsonl 保留 → AD2 事件化后 `degraded` / 重试次数已结构化 → 多实例需求出现时，启用 OTLP 导出接口对接既有 Collector（P3 演进项）。即：先把「值得观测的数据」做出来，再买「聚合观测的基础设施」。

### 3.6 被否决的方案

以下方案在调研或评审中曾被提出，全部否决；收录于此防止后续 spec 重复论证。

| # | 方案 | 否决理由 |
|---|------|----------|
| ① | 合并 Java 层，前端直连 Python Agent | 认证（jjwt / token 刷新）、行程状态机、PDF 导出、缓存与幂等仍需承载层，合并只是把职责搬进 Python；Agent 的 `X-Agent-Token` 将暴露到浏览器，破坏安全边界；README 已声明双后端是有意拆分（LLM 编排与业务状态解耦） |
| ② | WebFlux 全响应式重写 Java 层 | 需求是单向事件推送，SseEmitter 在 servlet 栈完全满足；全响应式要求 Service / Repository 全链路 reactive 化，重写成本与收益完全不成比例 |
| ③ | 更换 UI 库（Element Plus → Naive UI 等） | 现有 40+ EP 组件用法深度覆盖表单 / 表格 / 弹层；F4 包体积靠按需引入即可解决；视觉升级（§5）通过设计令牌与定制主题实现，不依赖换库 |
| ④ | WebSocket 替代 SSE | 需求是纯服务端 → 客户端单向推送；SSE 自带断线重连与 HTTP 语义（过代理 / 网关更友好），WebSocket 双向能力闲置且需额外心跳 / 连接管理 |
| ⑤ | 自研 Agent 编排替代 LangGraph | 现有 `unified_agent_graph` 图结构成熟（research → generate → reflect → format + mode 分流），问题（P3/P5/P8）在状态类型与 Prompt 管理，不在编排框架；自研重写零收益高风险 |
| ⑥ | 前端引入 GraphQL | REST + 三层契约同步（AD3）已覆盖需求；引入 GraphQL 需新增网关与 schema 管理层，复杂度不值 |

**共同否决判据**（后续新提案照此过滤）：凡「换栈 / 加平台 / 引双向能力解决单向问题」类提案，须先证明现有栈在原理上无法达成目标——仅「实现更优雅」「技术上更新」不构成充分理由。

#### 4.1.1 输入侧：`intent` 与 `requirements`

| PDF 导出 | 1.5s×60 轮询 export tasks（`:1322-1353`） | `events` 通道：`export_done`（复用连接） | 回退 export tasks 轮询 |

### 4.3 SSE 事件协议

#### 4.3.1 统一信封

```json
{
  "type": "day_done",
  "itineraryId": 123,
  "seq": 42,
  "ts": "2026-09-11T10:30:00+08:00",
  "data": { "dayNo": 1, "theme": "穗织小镇街区巡礼：祇园—二年坂—白川", "itemCount": 6 }
}
```

- `type`：事件类型（见 4.3.2）；
- `seq`：单 itinerary 内**单调递增**，客户端用于乱序检测与断线补发判断；
- `ts`：ISO-8601 带时区；
- `data`：各事件类型自定义 payload；
- 心跳 `heartbeat` 每 15s（防代理空闲断连）。

#### 4.3.2 事件类型表

| type | 通道 | data payload 字段 | 触发时机 | 示例 |
|------|------|-------------------|----------|------|
| `research_start` | events | `{domains: [str]}` | Python 三域研究启动 | `{"domains":["attraction","hotel","food"]}` |
| `research_done` | events | `{evidenceCount: int, degraded: bool, domains: [{domain, count}]}` | 研究完成（含降级标记，原则 4） | `{"evidenceCount":87,"degraded":false,"domains":[...]}` |
| `day_start` | events | `{dayNo: int}` | 单日开始生成 | `{"dayNo":1}` |
| `day_done` | events | `{dayNo: int, theme: str, itemCount: int, note: str}` | 单日落库完成，**前端可增量渲染当日卡片** | `{"dayNo":1,"theme":"穗织小镇街区巡礼…","itemCount":6,"note":"节奏：步行为主"}` |
| `butler_note` | events | `{length: int, preview: str}` | 管家扩写完成 | `{"length":520,"preview":"这趟行程以千恋万花…"}` |
| `degraded` | events | `{scope: str, reason: str, fallback: str}` | 任一环节如实降级（研究降级 / 单日降级 / 管家失败…） | `{"scope":"day_3","reason":"LLM 超时，已重试一次","fallback":"待研究草案"}` |
| `error` | events | `{code: str, message: str, retryable: bool}` | 不可恢复错误；`retryable` 决定前端是否展示重试按钮 | `{"code":"AGENT_TIMEOUT","message":"生成超时","retryable":true}` |
| `complete` | events | `{status: str, dayCount: int, degradedDays: [int], versionId: int}` | 终态汇总（含部分成功信息，`status`：COMPLETED / PARTIAL / FAILED） | `{"status":"PARTIAL","dayCount":3,"degradedDays":[3],"versionId":88}` |
| `chat_token` | chat-edit/stream | `{messageId: str, delta: str}` | chat 流式回复分段 | `{"messageId":"m1","delta":"好的，"}` |
| `chat_draft` | chat-edit/stream | `{messageId: str, plans: [..], baseRevision: int}` | plans 草稿推送（编辑流 §2.4.2） | — |
| `export_done` | events | `{taskId: int, status: str, downloadUrl: str}` | PDF 完成（导出流 §2.4.3，复用 events 通道） | `{"taskId":9,"status":"DONE","downloadUrl":"/api/export/9/file"}` |
| `heartbeat` | 两者 | `{}` | 15s 空闲心跳 | `{}` |

#### 4.3.3 Java↔Python 侧通道

Python 节点完成即发布事件到 Redis pub/sub topic `gen:events:{itineraryId}`；Java SSE 网关每实例订阅其服务的 itinerary 集合（`psubscribe gen:events:*` 或按需 subscribe / unsubscribe）并转发给对应 SseEmitter。**多实例就绪**：发布方无需感知 Java 实例拓扑，任一实例订阅同一 topic 即可转发。事件的权威状态以 DB 为准（事件只是通知，断线后靠 `GET /{id}` 对账，见 4.3.4）。

#### 4.3.4 断线重连策略

**推荐方案：客户端回退一次全量 `GET /{id}` 对账**（简单优先）：

1. fetch-event-source 自动重连（指数退避，上限 30s）；
2. 重连成功后**不回放 missed 事件**——客户端立即执行一次全量 `GET /{id}` 对账（detail 是单一数据源，幂等刷新即可恢复一致）；
3. 重连连续失败（如 3 次）→ 降级回轮询模式（现有 2.5s 轮询 + 熔断语义保留），并提示网络状态。

**备选方案（记录但不采用）**：Java 侧 Redis 短暂缓存最近 N=200 事件 + `Last-Event-ID` 重放——需 per-itinerary 环形缓冲与 TTL 管理，实现复杂；而生成事件本身可从 DB 全量推导，对账语义已足够。

**取舍依据**：Redis pub/sub 消息不持久是既定事实，与其在 Java 侧自建缓冲补齐，不如承认「事件即通知、DB 即真相」的分层——这也与原则 4 一致：宁可对账，不冒事件丢失后前端状态与库内不一致的险。

#### 4.3.5 完整事件序列示例（京都 3 日生成）

```text
seq 1   research_start   {"domains": ["attraction", "hotel", "food"]}
seq 2   research_done    {"evidenceCount": 87, "degraded": false, "domains": [...]}
seq 3   day_start        {"dayNo": 1}
seq 4   day_done         {"dayNo": 1, "theme": "穗织小镇街区巡礼：祇园—二年坂—白川", "itemCount": 6}
seq 5   day_start        {"dayNo": 2}
seq 6   day_done         {"dayNo": 2, "theme": "东山全景与主神殿对位", "itemCount": 5}
seq 7   day_start        {"dayNo": 3}
seq 8   degraded         {"scope": "day_3", "reason": "LLM 单日生成超时，已重试一次", "fallback": "待研究草案"}
seq 9   day_done         {"dayNo": 3, "theme": "神户生田神社（可选）与返程采购", "itemCount": 4}
seq 10  butler_note      {"length": 520, "preview": "这趟行程以《千恋万花》圣地巡礼为主线…"}
seq 11  complete         {"status": "PARTIAL", "dayCount": 3, "degradedDays": [3], "versionId": 88}
（heartbeat 每 15s 穿插，略）
```

读法：`degraded` 后仍出现 `day_done` 表示第 3 日以「重试成功 / 待研究草案」形态交付；`complete` 的 `status=PARTIAL` + `degradedDays=[3]` 保留如实记录——降级不隐藏（原则 4）。

### 4.4 Java↔Python 契约严格化

#### 4.4.1 裸 dict 端点 Pydantic 化清单

| 端点 | 现状（裸 dict） | 目标 Pydantic 模型（`app/schemas/`） | Java 对应 DTO |
|------|-----------------|--------------------------------------|----------------|
| `/v1/butler-note` | 请求 / 响应均无校验（P2） | `ButlerNoteRequest` / `ButlerNoteResponse`（含 `intent`，四段结构字段） | `AgentButlerNoteRequest` / `AgentButlerNoteResponse` |
| `/v1/poi-intros` | 同上 | `PoiIntrosRequest` / `PoiIntrosResponse`（intro 80–140 字 + `intent` 连接） | `AgentPoiIntrosRequest` / `AgentPoiIntrosResponse` |
| `/v1/poi-nearby` | 同上 | `PoiNearbyRequest` / `PoiNearbyResponse` | `AgentPoiNearbyRequest` / `AgentPoiNearbyResponse` |
| `/v1/city-guide` | 同上 | `CityGuideRequest` / `CityGuideResponse` | `AgentCityGuideRequest` / `AgentCityGuideResponse` |

clarify 透传（Java 侧 `Map/JsonNode`，J4）同步收编为强类型 DTO；Java→Python 全部调用点（`AgentServiceImpl`）改用上述 DTO，消灭 `Map<String,Object>`。

#### 4.4.2 wire 规范

- **信封**：沿用现有 `ApiResponse` 包装（code / message / data），不另发明格式；
- **命名**：wire 层 camelCase（Pydantic 用 `alias` / `alias_generator`，Java 默认），Python 内部 snake_case；
- **头**：`X-Agent-Token`（服务间认证）、`X-Request-ID`（链路追踪）、`X-Agent-Run-ID`（单次生成运行标识，日志 / 事件 / 用量三向关联）。

#### 4.4.3 契约版本策略

- 请求头 `X-Agent-Contract-Version`（当前值 `1`）：**先宽松后收紧**——初期 Java 发送、Python 记录不校验；Java / Python 同步升级完成后收紧为不匹配返回 4xx；
- 契约变更（新增可选字段除外）必须升版本号并双端同步发布；新增可选字段不升版本（向后兼容）。

#### 4.4.4 生成主契约三层同步核对表（防 V4 复发）

`GenerateResponse` 每新增一个字段，**必须同时落地五处，缺一即 CI 失败**（单测断言字段存在）：

| # | 落点 | 检查方式 |
|---|------|----------|
| 1 | Pydantic 模型（`app/schemas/trip.py`） | Python 单测断言字段存在 + 约束生效 |
| 2 | Java VO（`AgentGenerateResponse` 等） | Java 单测反序列化样例 JSON，断言字段映射 |
| 3 | 落库映射（`metadataJson` / 表列） | 落库抽样单测：mock LLM 返回 → 断言库内字段（承档案 M1 验收） |
| 4 | TS 类型（`types/itinerary.ts`） | 前端 CI 类型检查（strict TS，禁 `any` 逃逸，治 F5） |
| 5 | 前端渲染 | 组件测试断言字段渲染（含空态处理） |

**V4 的教训制度化**：五处中任何一处缺失 = 槽位空转或字段丢失，且无任何报错（现状 `whyThis` 在 Java 侧 grep 无命中即为例证）。此核对表把「人工记得改五处」变成「CI 强制五处同改」——这是 §2.1.2 基调③（契约先行）的最终落地形态。

**排版规则**（三轨字体的叙事分工强化）：

- **衬线展示层只承担「叙事标题」**：`trip_theme` 叙事条、每日 `theme` 叙事句——它们是手册的「章标题」；POI 名称、按钮、标签一律不用衬线，展示层不泛滥；
- **`why_this` 用正文小号**（body 0.85em）+ `--lp-why-ink`：它是注释不是标题，参与信息密度而不参与视觉竞争；
- **data mono 扩展到叙事数据**：`photo_spots.best_time` 时段、`day_options` 得失摘要中的数字；
- **`backup_plan` 条件句式**：`if` 从句斜体衬线、`action` 正文——「若…则…」的语法感即排版。

**色彩策略声明**：色彩不局限于暖橙——**主色青绿**（`--lp-accent`）承担品牌、导航 active 态、全部主操作按钮；**陶土橙**（`#bd6246`）仅作装饰序数与拍照徽标点缀；**叙事层**（`--lp-theme-accent` 渐变 + `--lp-branch-a/b` 蓝紫 / 大地色系）承担主题与分支表达。三层各司其职，禁止暖橙承担交互色（语义与对比度均不合格）。

**动效与可访问性底线**：全部流式动画遵守既有 `prefers-reduced-motion`——reduce 模式下降级为静态状态文案（如「生成中 · 第 2 / 3 天」）；叙事色与底色对比度须达 WCAG AA（正文 4.5:1、大字与图形 3:1）。

**令牌分层小结**：重构后 `--lp-*` 体系形成三层——**基础层**（bg / accent / 卡片 / 阴影：操作与容器）、**功能层**（预算 5 色板、EP 覆盖：既有）、**叙事层**（本节 6 组新令牌）。新组件取色规则：交互与状态取基础层，数据可视化取功能层，叙事字段渲染取叙事层；叙事色不得挪作按钮 / 链接等功能用途（语义混乱 + 对比度未按交互要求校验）。

- `trip_theme`（§4.1.2 顶层字段）用衬线展示层大字；**意图回显行**取用户 `intent` 原文（muted 小字）——「系统听懂了什么」首屏即见（S6 价值感知弱的前端对策）；
- 空态：无 `trip_theme` 时（历史行程 / 降级生成）整条隐藏，意图回显并入 head 卡副标题——有槽位无内容不渲染空壳（V4 教训的展示层落实）。


#### 5.3.3 why_this 次级行

每个 POI 卡片（拖拽列表项）描述之下新增一行：

#### 5.3.5 SSE 流式进度体验

替换现状生成中 banner（「已完成 x/y 天」+ 2.5s 轮询 `:762-786`）。流式状态机（store 内 `streamState`）：`idle → researching → day-{n} → butler → complete`，任一环节可进入 `degraded-{scope}`；UI 由状态驱动：

```text
┌ 生成中 ──────────────────────────────────────┐
│ ▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒  ← 研究阶段 · 骨架 shimmer  │
│ ── 研究完成：87 条证据 ──        ← research_done │
│ Day 1  ●●●●●●●●  ← 已点亮（theme 叙事句浮现）     │
│ Day 2  ▒▒▒▒▒▒▒▒  ← day_start · 微光进行中        │
│ Day 3  ○○○○○○○○  ← 待生成                       │
└──────────────────────────────────────────────┘
```

**事件 → UI 映射**（与 §4.3.2 事件类型表一一对应）：

| 事件 | UI 反应 |
|------|---------|
| `research_start` | 头部 shimmer 启动，全部日卡骨架态 |
| `research_done` | shimmer 停止 + 「研究完成：N 条证据」；`degraded: true` 时附「部分证据降级」提示 |
| `day_start` | 当日卡片转微光态 |
| `day_done` | 当日卡片点亮：theme 叙事句浮现 + items 摘要态 |
| `butler_note` | 管家卡淡入 + preview 摘要 |
| `degraded` | 对应 scope（日卡 / 管家区）挂「已降级 · 原因」角标 |
| `error` | `retryable` 展示重试按钮；不可重试展示失败态 |
| `complete` | 状态条收束；`PARTIAL` 保留 `degradedDays` 角标如实展示 |

- **三阶段体验**：研究阶段头部 + 全部日卡骨架 shimmer（`--lp-stream-glow`）→ `day_done(dayNo)` 到达时当日卡片**渐次点亮**（theme 叙事句先浮现；事件携带摘要 `{dayNo, theme, itemCount, note}`，§4.3.2——卡片先以摘要态点亮，随后经一次 detail 对账换取完整 items，`day_done` 已触发单 key 缓存精确失效，对账成本低）→ `butler_note` 完成后管家卡淡入；
- **降级可见**（原则 4 的展示层）：`degraded` 事件在对应日卡挂「已降级 · 原因」角标（`--lp-why-ink` + 警示描边）；`complete` 为 `PARTIAL` 时保留 `degradedDays` 列表如实展示，不隐藏；
- **断线无感降级**：`useItineraryStream`（§5.4）按 §4.3.4 重连（指数退避，上限 30s）+ 全量对账；连续 3 次失败自动回退 2.5s 轮询（原熔断语义保留），用户仅见底部状态条「网络不稳定，已切换保守模式」；
- **聊天流式**：chat 回复打字机效果逐段渲染（`chat_token`），替代现状 70s 长阻塞零反馈（`:560-616`）；`chat_draft` 携带的 plans 草稿以结构化变更卡呈现（变更摘要 + diff），用户「应用」后乐观更新 + `baseRevision` 提交（§2.4.2）；
- **导出**：`export_done` 到达即亮起下载入口（复用同一 events 通道），替代 1.5s×60 轮询（`:1322-1353`）。

**composables**：

| composable | 职责 |
|-----------|------|
| `useItineraryStream(itineraryId)` | SSE 订阅（fetch-event-source，POST + Bearer）：事件分发到 store reducer、`seq` 乱序检测、断线指数退避重连（上限 30s）、重连成功全量对账一次、连续 3 次失败降级回轮询并提示（§3.2 接入要点全量落实） |
| `useItineraryActions(itineraryId)` | 增删改拖拽动作封装：乐观更新 + 失败回滚 + revision 冲突（409 → 提示刷新对账）；酒店替换 / 备选采纳 / 草稿应用统一经此入口 |

**Pinia itinerary store**（治 F3）：

- `detail` 为单一数据源（days / items / 叙事字段 / `revision` / `streamState`）；SSE 事件以 **reducer** 形式落入——`day_done` → 更新当日摘要 + 状态迁移、`degraded` → 打降级标记、`complete` → 收束状态；
- 消灭现状 `detail.value` 10+ 处手工同步——组件只读 store，变更只经 `useItineraryActions`；
- 酒店选择收敛到 store（localStorage 仅作离线缓存，读写经 store 单点）；
- `revision` 随每次成功变更递增，409 冲突触发对账刷新。

**store 核心状态**：

| state | 说明 |
|-------|------|
| `detail` | 行程全量（days / items / 叙事字段 / revision），唯一可写数据源 |
| `streamState` | SSE 流式状态机（§5.3.5：idle / researching / day-{n} / butler / complete / degraded-{scope}） |
| `chatDraft` | `chat_draft` 草稿数据（变更卡），应用或取消后清空 |
| `pendingOps` | 乐观更新中的操作队列（失败回滚与冲突提示依据） |

**api 层与类型拆分**（治 F5 / F8）：

- `api/index.ts`（459 行、45+ 函数 + 类型 + 常量混编）拆为 `api/{auth, itinerary, amap, export, admin}.ts` 按域模块；
- `types/` 独立并**对齐第 4 章**：补 `tripTheme / whyThis / dayOptions / photoSpots / practicalNotes / backupPlan` TS 定义；消灭 `draftPlans: any[]`、`ItineraryChatMessage.plans: any[]`、`AMap / L: any` 类型逃逸（strict TS，CI 类型检查，AD3 前端侧）；
- 删除 `BaseMap.vue` 死代码；`CITY_COVERS` 与 `DESTINATIONS` 合并为 `constants/covers.ts` 单一来源（治 F9）；`geo.ts` 城市 / 省份硬编码表迁入 constants 并标注维护入口。

## 7. 潜在风险与取舍

### 7.1 风险与对策

**识别方法**：三类来源交叉——① §1 的 42 条问题在重构中的「治疗副作用」（如 AD5 叙事密度带来 R1 / R8）；② 新架构引入的新风险面（SSE 的 R2、intent 的 R10、store 化的 R13）；③ 档案 §10 已识别并验证过的风险（R7 / R9，直接继承并更新对策）。概率按「触发频率 × 现状是否已有同类先例」评估。

**风险地图**：13 项风险按里程碑分布——M0 / M3 契约与叙事（R1、R6、R8）；M2 流式与统一（R2、R4、R11）；M4 前端（R5、R13）；横切项（R3 重构期可用性、R7 / R9 / R10 价值层、R12 观测）。概率「高」两项（R1、R8）均为 AD5 叙事密度的直接代价，已在 §4.1.2 字段限额中前置化解。

**分级响应**：高概率（R1、R8）进入 M3 验收硬门槛，未化解不得合并；中概率项内嵌到对应里程碑交付物（§6.2 各「风险关联与回退」行）；低概率（R12）记录观察、P3 演进承接。

**登记册维护**：R1–R13 为定稿基线；实施期间新增风险按同模板（风险 / 影响 / 概率 / 对策）追加编号并入风险地图，已消解的风险标记关闭而不删除（保留决策痕迹）；里程碑验收时逐项复核风险状态（§6.2 共同纪律第 3 条的组成部分）。

**监控指标**（随 M5 评测集固化、日常抽检）：R1 对应「校验失败率 / 单日降级率」；R2 对应「SSE 重连次数 / 降级轮询占比」；R4 / R11 对应「单行程 LLM 调用次数与总耗时」（M0 基线对照）；R8 对应「JSON 解析失败计数」。指标异常即触发对应对策评审，而非等用户反馈。

**降级链总览**（各风险兜底终点的系统性视图，原则 4 的落实图谱）：

**边界澄清**：「不做」不等于永久否决——第 7 项（多实例观测）与 P3 相关项（主题知识库、用户记忆）为**条件触发项**：多实例部署需求出现时按 §3.5 OTLP 演进路径启动；知识库 / 记忆在价值线 M5 回归达标后再评估。第 1–6 项为架构性否决（§3.6），重启论证须先修订本方案。

**为什么这样取舍**——三判据收束（「做什么」「不做什么」由同一组判据推出，而非两份独立清单）：

1. **可信骨架不破**（否决线）：所有「做」的项无一触碰内容来源与溯源链路，叙事与事实分层标注（§8 矩阵逐格核对）；凡可能牺牲可信换体验的设计一律退回——这条否决线同时解释了「不做」第 8 项（OTA 房价引入绕过证据链的外部事实源）与第 9 项（长期记忆引入跨会话的数据信任假设）。
2. **最小代价换最大价值**（排序线）：AD 按收编问题数 ÷ 改造成本排序——契约（9 条）与 SSE（6 条）优先落地；全栈零更换、依赖净新增 1 个（§3.1）；「不做」清单的共同特征是高成本、零问题编号收益，或属于 §3.6 已否决方案的变体。
3. **渐进可回退**（执行线）：每条新路径保留旧路径降级（SSE 回轮询、流式编辑回阻塞端点、逐日统一回 fast-path），里程碑独立上线、独立回退（§6.1）；「不做」第 7 项（多实例合规）同样由此推出——单实例阶段的回退空间还不需要为多实例支付复杂度。

凡不满足三判据的新提案（换栈 / 加平台 / 引双向能力解决单向问题），按 §3.6 共同否决判据过滤；本取舍声明与 §8 兼容性矩阵共同构成后续一切 spec 的评审基准。

**矩阵读法**：40 格中无一格为「冲突」；「显式增强 / 防护网」6 格（AD2-④、AD3-③④、AD4-②⑤、AD6-④）表明重构不仅不破坏原则、反而在工程上强化其可见性；「重点管控」1 格（AD1-⑤）是唯一因新增输入面而需重点盯防的组合，对策已在 §7.1 R10 落实并进入 M1 交付物。

**新增字段的原则适用**（矩阵之外的逐字段核对）：`intent / requirements`（输入面，⑤ 定界符包裹）；`trip_theme / theme / why_this`（叙事面，① 100% LLM 生成 + ② `value_kind=generated` 与事实分层）；`photo_spots / practical_notes / backup_plan / day_options`（细节面，同叙事面处理）；SSE 事件 payload（进度面，只承载摘要、不承载正文）。每个新字段的五原则归属已在 §4.1 定义处逐一标注，本矩阵按 AD 维度收束。

### 8.2 逐 AD 收束声明

- **AD1**：意图贯通扩大了用户输入面，唯一新增风险是注入面扩大——以原则 ⑤ 的定界符 + 数据非指令声明为闸门。系统因此「懂你要什么」，但懂的是证据允许的懂法。
- **AD2**：流式化把降级从静默吞掉变成显式事件，是原则 ④ 的工程化落地；事件只承载进度，行程内容仍只来自已校验的生成结果。
- **AD3**：契约是原则 ②③④ 的防护网——「未标注 unverified」「降级冒充正常」从用户侧显形提前到 CI 校验期；V4 槽位空转的教训由此制度化。
- **AD4**：模板化把引用规范、防注入声明、降级文案收进共用片段单点维护，消除「改一处忘一处」的漂移面。
- **AD5**：叙事与事实严格分层——`why_this` 写得再像实锤也不影响 `verification_status`；「可信 × 意图」相乘而非互换。
- **AD6**：纯编排治理，不触内容与溯源；显式状态机反而让「部分成功 / 已降级」第一次变得如实可查。
- **AD7**：纯展示与状态层重构；溯源标签与降级提示的可见性在 §5.3.5 中被强化（降级角标、PARTIAL 状态展示）而非弱化。
- **AD8**：路径合并不改内容来源；单日失败如实标注待重试，比整程 180s 超时全量失败更诚实。

八条声明的公共结论：AD1–AD8 与五原则的关系是「其余兼容、六处增强、一处重点管控、无一处冲突」——重构扩大了系统能力面，同时把原则的执行从「约定」升级为「工程机制」（CI 校验、事件推送、模板单点）。
