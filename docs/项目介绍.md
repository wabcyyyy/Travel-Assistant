## 一、项目定位与技术全景

### 1.1 做了什么

一个**端到端的 AI 旅行规划系统**：用户输入目的地、天数、人数和偏好，Agent 自动规划每日行程（景点→餐饮→酒店），生成带时间轴、地图路线、预算明细的完整方案，并支持自然语言对话式二次编辑。

**核心功能清单**：

| 功能 | 说明 |
|------|------|
| 行程生成 | 输入城市/天数/人数/偏好 → AI 生成每日景点+餐饮+酒店+时间轴 |
| 行程边界 | 单次新建、对话扩展和草稿确认统一最多 7 天，超限请求直接拒绝 |
| 对话编辑 | 用自然语言修改已生成的行程（删景点、换酒店、改时间、加天数等） |
| 酒店推荐 | 按档次筛选候选酒店，展示房型/价格/季节系数，支持一键替换 |
| 城市引导 | 不确定去哪？AI 对话帮你锁定目的地 |
| 槽位澄清 | 信息不全时自动追问（目的地/天数/人数），前端表单联动 |
| 地图可视化 | 高德地图 SDK 展示每日路线、景点坐标、酒店位置 |
| 预算面板 | 按门票/餐饮/交通/酒店分类汇总，支持预算上限预警 |
| PDF 导出 | 异步导出行程为 PDF，支持轮询下载 |
| 管家讲解 | 行程完成后 AI 生成整体规划思路讲解 |
| 景点介绍 | 批量为每个景点生成详细介绍文本 |

  ↕ HTTP/REST (JWT Bearer Token)

  ↕ HTTP/REST

  ├── LangGraph (统一生成图 trip_graph：mode=day/trip + 多 Agent 研究编排)
  ├── 研究层 (酒店/景点/美食研究 Agent ×3 + Supervisor 缺口补查)
  ├── ChromaDB (RAG 向量检索)

**数据流**：前端 → Java 后端（建单/异步编排）→ Python Agent `generate-day`（进入统一图 `mode=day`：生成→反思→重试→最后一次重试）→ Java 落库、预算重算和清缓存 → 前端轮询展示渐进结果。`/v1/generate` 走同一张图 `mode=trip`（parse→research→generate→reflect→format；research = Supervisor 并行派发三个研究 Agent，证据缺口只补查对应域），用于直接调用和离线评测。对话编辑走 `chatTurn` 闭环：Java 组装上下文 → Python Agent 做动作决策 → Java 校验/用户确认/事务落库。

## 二、核心架构设计亮点

### 2.1 "LLM 当规划者，代码当执行者"的分离范式

这是整个项目最核心的架构决策。**行程写入链路**不用模型自由 Function Calling——LLM **只负责结构化意图输出**（JSON），所有写操作由确定性代码执行并校验。  
**只读辅助链路**（如 `poi_intros` 景点介绍）允许受限 FC：模型可从 Tool Registry 调用只读工具（`search_pois` 等）补事实后再写文案，失败回退单轮生成；**绝不注册写库/删行程类工具**。

**为什么写入链路不直接用 Function Calling？**

旅行规划是**强正确性**场景——时间冲突、地理不合理、价格虚高都会直接损害用户体验。让 Agent 自主决定写工具调用顺序会导致不可控的规划路径。我们选择让 LLM 做它最擅长的事（结构化决策），用确定性代码做它不擅长的事（精确执行、事务写入、版本控制）。

**具体体现**：

**1. 行程生成链路**（`generators.py:137-198`）

LLM 只输出结构化 JSON（`daily_plans` + `budget_estimate`），景点/餐饮/酒店全部从候选列表中选择，价格取候选原值：

```python
# generators.py:150-156 — System Prompt 中的反幻觉约束
"景点和酒店必须从候选列表中选择，不得编造。"
"每个行程项的 cost 必须直接取候选数据中的 ticket_price 字段原值"
"严禁自行编造价格。"
```

首版生成的 API 调用目前通过 `Prompt Schema` 要求结构化 JSON，再经过解析、字段补水、确定性校验和 fallback；并非所有生成请求都启用了 API 层 `response_format=json_object`。对话编辑链路才显式启用 JSON mode，见 `chat_draft/decide.py`。

**2. 对话编辑子系统**（`chat_draft/decide.py:46-87`）

封闭动作集把任意自然语言归约到 5 种有限决策：

| 动作 | 场景 | 输出 |
|------|------|------|
| `hotel_proposal` | 涉及住宿/酒店变更 | 酒店请求（从候选列表选） |
| `plan_update` | 小修（删/加/移动/改时间） | `patches` 补丁列表 |
| `rewrite_plan` | 大改（改天数/整体重排） | 完整 `plan_document` |
| `clarify` | 信息不足/冲突 | 澄清问题 |
| `no_change` | 无需修改 | 空操作 |

```python
# decide.py:51 — 动作集定义
"1) hotel_proposal：凡涉及住宿、酒店、宾馆、房型或某酒店品牌，无论措辞，都必须用它；"
"2) plan_update：对现有行程'小修小补'——移动单个项目、改时间、删/加个别景点"
"3) rewrite_plan：对行程做'大改/重生成'，例如改变总天数"
"4) clarify：信息不足、存在冲突或无法安全安排时使用"
"5) no_change：确实无需修改时使用"
```

**3. Java 侧的校验层**（`ItineraryPlanApplyService.applyPlans`）

从 AI 消息的 `plansJson`（权威数据源）读取、逐项校验结构合法性、事务内逐条落库，防止模型"偷偷改数据"。

**面试价值**：这体现了对 LLM 局限性的深刻理解——模型擅长"想"但不擅长"做"，与其依赖不稳定的 tool calling 协议，不如让模型做它最擅长的事（结构化决策），用确定性代码做它不擅长的事（精确执行、事务写入、版本控制）。

### 2.2 异步渐进式生成 + 伪流式可见

行程生成不是一次性返回，而是**逐日增量生成**，解决了真实的产品问题：生成较长行程时，用户可以先看到已完成日期，而不是面对整段请求的空白 loading。当前项目没有对“首日固定 3 秒”做专项基准测试，因此这里不把 30 秒到 3 秒作为硬性性能指标。

**完整流程**（`ItineraryAsyncPlanner.java:50-94`）：

```java
@Async
public void planDays(Long userId, Long itineraryId, GenerateRequest request, JsonNode context) {
    // 1. 等待壳数据可见（最多重试 10 次，每次 500ms）
    for (int i = 0; i < 10; i++) {
        if (mainMapper.selectById(itineraryId) != null) break;
        Thread.sleep(500);
    }
    List<String> usedNames = new ArrayList<>();  // 跨日去重状态
    String chosenHotel = null;                    // 跨日酒店状态

    for (int dayNo = 1; dayNo <= request.getDays(); dayNo++) {
        // 2. 构建 payload（含 used_names/chosen_hotel/context）
        payload.put("used_names", usedNames);
        payload.put("chosen_hotel", chosenHotel);
        payload.put("context", context);

        // 3. 调用 Python Agent 生成单日
        JsonNode node = agentService.generateDay(payload);

        // 4. 落库 + 更新跨日状态
        persistDay(itineraryId, request, dayNo, plan);
        plan.getItems().forEach(i -> usedNames.add(i.getPoiName()));
        evictCache();  // 清缓存，前端轮询可见新数据
    }
    finish(userId, itineraryId, request);  // 5. 设 status=2 + 生成管家讲解/景点介绍
}
```

**关键设计决策**：

1. **建单壳先行**（`ItineraryGenerationService.generate`）：立即建主表 status=1（生成中）+ 预创建 N 个空日，**不加 @Transactional**——异步线程必须在壳数据提交后才启动，否则查不到单
2. **跨日状态管理**：Java 侧维护 `usedNames`（已选景点名集合）和 `chosenHotel`（已选酒店名），逐日回传给 Python，确保整条行程的连贯性（不重复选同一景点、住同一家酒店）
3. **每天完成即清缓存**：`evictCache()` 确保前端轮询能看到最新数据
4. **可选增强不阻塞**：管家讲解和景点介绍在 `finish()` 中作为可选增强执行，失败只 warn 不影响 status=2（完成状态）

**前端渐进展示效果**：用户可以看到“第1天已完成，第2天生成中……”的 loading 状态；该设计减少一次性等待的空白感，但实际耗时仍受 LLM、网络和候选数据规模影响。

### 2.3 多层降级容错体系

这是项目工程化程度最高的部分，形成了"五层防御纵深"：

| 层级 | 机制 | 代码位置 | 说明 |
|------|------|---------|------|
| 1 | **宽松 JSON 解析** | `generators.py:295-304` | 剥 markdown 代码围栏 + 首尾大括号截取 |
| 2 | **self-repair 重试** | `decide.py:110-124` | 发专门修复请求："只输出语法正确的JSON" |
| 3 | **反馈回喂重试** | `workflow.py:88-89` / `decide.py:183-201` | 校验问题作为 feedback 注入 prompt |
| 4 | **如实降级（LLM-only）** | `workflow.py`（重试→待研究草案） | LLM 失败重试一次后返回待研究草案；`fallback_generate` 仅保留给 `eval_baselines` 消融评测，非生产路径 |
| 5 | **签名校验** | `decide.py:218-225` | `_hotel_signature` 检测模型篡改住宿数据 |

def _parse_json(raw: str) -> dict:
    text = raw.strip()
    if text.startswith("```"):
        text = text.split("\n", 1)[-1]
        text = text.rsplit("```", 1)[0]
    start = text.find("{")
    end = text.rfind("}")
    if start == -1 or end == -1:
        raise ValueError("LLM 输出中未找到 JSON")
    return json.loads(text[start : end + 1])
```

### 3.2 RAG 混合检索

检索策略因数据类型而异，每种 POI 都有自己的最优检索路径：

**景点检索**（`tools.py:78-84`）：

```python
def search_attractions(city: str, preferences: list[str], limit: int = 30) -> list[dict]:
    # poi_store.search 内部同时执行语义召回和词法召回，再用 RRF + 业务分数重排
    hits = poi_store.search(
        _build_query(city, preferences), city=city, category="attraction",
        limit=limit, preferences=_expand(preferences),
    )
    if not hits:
        # 索引不可用或无结果时，回退 MySQL 权威查询
        hits = poi_repository.search_pois(city, category="attraction", limit=limit)
    return _sort_by_preferences(hits, preferences)[:limit]
```

**酒店检索**（`tools.py:95-103`）——优先知识库（完整可枚举）：

```python
def search_hotels(city: str, limit: int = 6) -> list[dict]:
    # 1. 优先 MySQL 全量枚举（酒店数量有限且需要完整信息做价格比较）
    rows = poi_repository.search_pois(city, category="hotel")
    # 2. 省级目的地展开到具体城市（如"浙江省" → "杭州"+"宁波"+"温州"）
    if not rows and city in DESTINATION_CITIES:
        rows = poi_repository.search_pois_by_cities(DESTINATION_CITIES[city], category="hotel")
    # 3. 向量召回兜底
    return poi_store.search(f"{city} 住宿", city=city, category="hotel")[:limit]
```

**为什么酒店不走向量检索？** 因为酒店推荐需要全量候选做价格/档次比较，向量召回可能漏掉当前档次的酒店，导致推荐偏差。

**混合检索实现**（`rag/retriever.py` + `rag/store.py`）：

- **召回**：BM25 风格词法召回 + Chroma 语义召回，使用 Reciprocal Rank Fusion（RRF）合并，并叠加偏好、评分和预算业务分数
- **默认 Embedding**：中文按单字、英文按词切分 n-gram → `zlib.crc32` 映射到 256 维哈希桶 → L2 归一化。它是离线的词法特征近似，不应表述为真正的预训练语义模型
- **可选 Embedding**：安装 `sentence-transformers` 并配置 `RAG_EMBEDDING_PROVIDER=semantic` 后，可使用本地语义模型；模型不可用时自动回退到 hashed provider
- **ChromaDB**：PersistentClient 持久化，启动时从 MySQL 全量重建索引保证一致性
- **Metadata 过滤**：`$and` 组合 city + category 过滤

## 六、面试深度问题预判与回答要点

### Q1: 为什么不用 LangChain Agent / AutoGPT？

**答**：旅行规划是**强正确性**场景——时间冲突、地理不合理、价格虚高都会直接损害用户体验。让 Agent 自主决定工具调用顺序会导致不可控的规划路径。我们选择"LLM as planner, code as executor"范式：LLM 只做结构化决策（5 种封闭动作），所有执行由确定性代码完成并多重校验。这在可控性、可调试性、成本可控性上都优于 fully autonomous agent。

**追问：那你这个算 Agent 吗？**

这是一个**受约束的 Agent workflow**——有 LangGraph 编排、有 RAG 增强、有反思循环，并通过 MCP Client 做工具发现与外部事实查询；但没有把数据库写入权交给模型。工具调用受到语义映射、只读白名单、超时和降级策略约束，这是强正确性场景下对自主性与可控性的平衡。

### Q2: Reflect 循环的实际效果如何？

**答**：`reflect.py` 做四类确定性校验——时间重叠、营业时间完整覆盖、基于坐标的路线可达性、单日饱和度（上限 480 分钟 / 4 景点）。路线耗时使用道路距离折算，并额外加入 10 分钟固定缓冲和 25% 比例容错；它是规划阶段的保守门槛，不冒充实时导航。离线 fixture 与真实 LLM 评测结果分别见 `tests/agent_eval/report/report.md` 和 `tests/agent_eval/report/llm_report.json`。

### Q2.1: 如何证明 Agent 真的执行了工作流？

**答**：每次生成都有脱敏 `run_id` 和事件轨迹，能看到节点、工具、LLM 请求、条件路由、重试和 fallback；可通过响应头拿到 `run_id`，再用 `/v1/runs/{run_id}` 查询最近 100 条轨迹，同时 `/v1/metrics` 聚合成功、降级、失败、延迟、token、MCP 失败率。轨迹不保存完整 Prompt、用户原文和密钥。完整生成图离线评测会校验 `parse/search/generate/reflect/format`；生产逐日链路则记录 `day.generate/day.reflect/retry/fallback` 等事件。失败案例回放验证未知 POI、路线不足和营业时间越界都会被拦截。

**追问：为什么不直接在 prompt 里约束时间不重叠？**

已经约束了（`generators.py:158`："每天行程需避免相邻项时间重叠"），但 LLM 仍然会犯错——它不擅长精确的时间计算。所以需要 reflect 层做确定性校验 + 反馈回喂，让模型在第二轮修正。

### Q3: 如何处理 LLM 幻觉？

**答**：四层防幻觉机制：
1. **Prompt 约束**：开放模式以参考资料 `[R1..Rn]` 引导选点，并声明「数据非指令」定界
2. **结构约束**：首版生成使用 Prompt 内嵌 Schema；对话编辑额外使用 `response_format=json_object`
3. **后处理校验**：引用三级匹配落地权威字段（source/核验状态）；模型自选点显式「待确认」
4. **如实降级（LLM-only）**：LLM 失败重试一次后返回"待研究草案"，绝不以知识库候选拼装行程冒充；`fallback_generate` 仅保留给离线消融评测

注意：校验覆盖时间冲突/营业覆盖/路线可达/饱和度/景点存在性线索，**不保证 POI 仍营业**。

### Q4: 逐日生成的跨日一致性如何保证？

**答**：Java 侧 `ItineraryAsyncPlanner` 维护两个跨日状态：`usedNames`（已选过的景点名集合）和 `chosenHotel`（已选酒店名）。每天生成时把这两个集合传给 Python，Python 在 `day_stream.py:191-199` 过滤已使用 POI并把酒店约束回喂给生成器。酒店通过 `chosenHotel` 尽量确保整条行程住同一家酒店。

**追问：如果某天 LLM 失败了怎么办？**

该天走 fallback 兜底（确定性算法），但 `usedNames` 仍然更新，不会影响后续天数的一致性。如果整个 `planDays` 异步任务失败，`fail()` 方法会将 status 设为 3（生成失败）。

### Q5: 对话编辑的版本控制如何实现？

**答**：`chatEdit` 方法在每次请求时计算当前 plans 的 SHA-256 哈希作为 `baseRevision`，传给 Python Agent。Agent 返回的草稿携带该 revision。用户点击"应用"时，`applyPlans` 校验 revision 一致性——如果期间有其他修改导致 plans 变化，revision 不匹配则拒绝应用，防止旧草稿覆盖新数据。

### Q6: 性能优化做了哪些？

**答**：
- **Redis 缓存**：行程详情使用 `@Cacheable`，编辑后 `@CacheEvict` 清除
- **图片获取链路**：有界 LRU 缓存；数据源按 Wikipedia → Unsplash → 高德 POI 图片顺序降级
- **联网查询限额**：`MAX_LIVE_QUERIES=3`，防止 LLM 联网搜索成本失控
- **对话历史截断**：Java 最多传 20 条，Python 决策最终取 4 条，每条最多 800 字符
- **前端路由懒加载**：`() => import(...)`，首屏只加载必要代码
- **渐进式生成**：逐日落库 + 清缓存，前端轮询可见新数据

### Q7: 开放模式（未知城市/国外目的地）怎么处理？

**答**：LLM-only 口径下所有城市统一走开放模式（`_llm_open_day` / `_llm_open_trip`），知识库只是证据。生成前 `research` 节点由 Supervisor 并行派发酒店/景点/美食三个研究 Agent 收集证据包（LLM 规划检索策略、评估充分性、不足补查一轮）；LLM 选点后坐标落地走 provider chain：高德（国内）→ Google Places（可选，需 key）→ OSM Nominatim（国外免 key，真实坐标）。国外城市生成照常出行程且坐标/地图/路线可用；校验发现"未安排任何景点"类证据缺口时，Supervisor 只重派发景点研究 Agent 补查而非整体重生成。开放模式状态恒为 `degraded`（关键事实需出发前复核），该路径依赖外部服务，不能与本地权威候选约束路径等量齐观。

### Q8: 如果让你重新设计，会改什么？

**答**（展示自我反思能力）：

1. **语义检索升级**：当前默认使用 crc32 哈希 n-gram 做离线词法特征；虽然已预留 `sentence-transformers` provider，但还应补充真实语义模型的离线评测和资源治理
2. **消息队列**：当前用 Spring `@Async` 内存线程跑异步生成，服务重启会导致"生成中"状态的行程永久卡死。应该引入 RabbitMQ/Kafka 做任务持久化
3. **可观测性**：当前是单进程内存指标和最近 100 条脱敏 Trace，生产环境需要接入 Prometheus/OpenTelemetry + Grafana，并增加跨实例 Trace 存储与采样策略
4. **记忆增强**：当前对话记忆是无状态的滑动窗口，应该引入 summary memory（定期压缩历史）和 user profile（长期偏好画像）
5. **流式响应**：当前是请求-等待-响应模式，应该用 SSE/WebSocket 实现真正的流式输出，用户体验更好
6. **MCP 能力扩展**：当前已接入高德官方 MCP 的只读 POI 查询适配，默认关闭且失败可降级；下一步可将天气、公交路线、地理编码和距离测量等能力接入更完整的外部事实链路。

### 7.2 业务与架构局限

2. **开放模式行程项大量「待确认」**：LLM 自选点 + 高德/Google/Nominatim 落坐标；Reflection 验时间与路线可达，**不验「店还在不在」**。
3. **双后端是演示/职责拆分**：Java 管鉴权/状态机/异步/PDF，Agent 管智能；不是唯一生产形态。
4. **生成编排已统一**：`trip_graph.unified_agent_graph` 一张 StateGraph，`mode=day`（逐日）/ `mode=trip`（整段）分流；事实层 `day_stream`，产品口径 `generation_core`，门面 `workflow`/`day_workflow`。
5. **单机限制**：进程内限流/缓存/Trace，多实例需换 Redis/集中存储。
6. **第三方合规未做生产审计**：Wikivoyage CC BY-SA 署名与 ShareAlike、Nominatim UA/限流、Google Places 缓存条款、Unsplash API 政策均需产品化时再审。

## 八、项目亮点总结

> 这是一个工程化程度较高的 AI 旅行规划系统，核心亮点是：
>
> 1. **"LLM 当规划者、代码当执行者"的分离范式**——LLM 只做结构化决策，所有执行由确定性代码完成并多重校验
> 2. **多层降级容错体系**——宽松解析 → self-repair → 反馈回喂 → 如实降级草案 → 签名校验（LLM-only，生产无确定性兜底）
> 3. **异步渐进式生成**——逐日增量生成 + 跨日状态管理，让前端可以先展示已完成日期
> 4. **对话编辑的版本控制与 Human-in-the-loop**——草稿确认机制、SHA-256 版本校验、酒店签名防篡改
> 5. **封闭动作集提示词设计**——把任意自然语言归约到 5 种有限决策空间
> 6. **RAG 混合检索**——BM25 风格词法召回 + Chroma 语义召回，RRF 融合后再做偏好/评分/预算重排；酒店保留全量可枚举候选
> 7. **完整的降级链路**——LLM 失败重试后如实返回待研究草案；国外目的地经 Nominatim 免 key 落真实坐标；每层降级写入 trace 与 metrics，前端如实展示 degraded 原因
>
> 覆盖了从 LLM 结构化输出、RAG 检索、封闭动作集提示词、异步编排到事务落库的完整链路。
